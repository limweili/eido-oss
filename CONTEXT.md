# Eido Context

## Product

Eido is a free visual thinking board. It has no Eido account, subscription, credits, or paywall. Online AI and keyed web tools use provider access supplied and funded by the user (ADR 0051). Users place cards on a canvas, connect them, run AI workflows, keep generated versions, and replay the meaningful evolution of the board over time.

## One Graph, Three Views

The board is one graph of thoughts used three ways: the **canvas** (what the user sees and touches), the **semantic context** (how thoughts feed each other as meaning), and **execution** (how connected thoughts run as AI work). All three are projections of the same saved graph — none owns separate truth. See `docs/foundations/` and ADR 0011.

## Language Boundary

Use **Card** and **Connection** in product language, user-facing copy, and
domain documentation. Use **node** and **edge** only at the React Flow/Xyflow
adapter boundary or when another low-level graph API requires those terms.
`src/canvas/Board.tsx` is the primary translation seam.

## Glossary

- **Board**: The user's saved workspace: cards, connections, outputs, runs, timeline events, settings, and metadata.
- **Profile**: The app-managed local collection of a person's Ideas, Mod library, device-level settings, and recovery state on one installation. A Profile can contain many Boards and is not automatically shared across devices.
- **Portable Export**: A user-controlled, versioned copy of Eido data that can be verified and imported into another Profile. It is a transfer and backup contract, not the live editing authority or a recovery working copy.
- **Agent Gateway**: The local, versioned contract through which an external AI agent inspects Eido, requests bounded Board/Profile changes, or delegates a live Ask Chain. The gateway is a client of Eido's normal mutation and execution rules, never a second persistence writer or AI engine.
- **Projection**: A way of using the one graph (canvas, semantic context, execution, playback). Projections derive state from the graph and must be rebuildable from it.
- **Context Layer**: The seam that answers "which cards and connections feed this card, in what order, and why" as deterministic, explainable data. See `docs/foundations/context-layer.md`.
- **Context Policy**: A named, versioned rule set for a context query: hop depth and which strengths, polarities, and roles to follow. Same graph + same policy = same answer.
- **Execution Plan**: A versioned, serializable description of which steps will run over which cards, derived from the graph before anything runs. Today's runs are single-step plans; chains are longer plans of the same shape. See `docs/foundations/execution-layer.md`.
- **Step**: One unit of execution in a plan: a run over one card with inputs selected by a context policy, producing a provenanced output version.
- **Chain**: Ask AI cards feeding each other through their results. Notes are static context and never run; a chain exists only where a result card is another Ask's input. Running an Ask reruns that target, heals the minimum stale upstream chain, and reuses fresh upstream steps (ADR 0014).
- **Stale**: A result whose recorded sources no longer match the live board, or whose upstream step re-ran. Stale is what a chain run heals; fresh upstream steps are reused, while the pressed or delegated target reruns.
- **Compaction**: Replacing a card's full text with a cached AI summary when an Ask's context exceeds its budget — weakest links and bottom-of-order first, task text and Mods never, always visible to the user (ADR 0015).
- **Card**: A visual unit on the board. Current card kinds include notes, Ask AI cards, result cards, mods, groups, conversations, and titles.
- **Card Deep Link**: A copyable `eido://app/...` URL naming an Idea, a Card, and optionally the viewport it was copied from. It is Eido's handoff idiom — a human points a person or an agent at a place on the board by sharing one. The card identity is the authoritative anchor; the viewport numbers are a hint that may go stale.
- **Passive Card**: A content-complete Card representation that is visible or prepared but does not currently own the Card's internal interactions. Passive describes interaction authority, not a cached-image or static-renderer technology (ADR 0023).
- **Reading Residency Window**: The bounded, viewport-led set of detailed Cards kept prepared through a preload margin, direction-aware look-ahead, and exit hysteresis. Live Card ownership can retain a Card outside this ordinary window (ADR 0023).
- **Live Card**: A Card currently owning one or more full-interaction lifecycles: accepted activation, focus, interaction-ready selection, editing, internal scrolling, controls, an eligible gesture, keyboard focus, or active media. Hover alone is never a Live owner. It remains Live until every owner ends (ADR 0023).
- **Active Editor**: A Live Card currently owning an editor, caret, text selection, or composition session. Active Editors are always Live Cards, but not every Live Card is editing (ADR 0023).
- **Hot Interaction Authority**: The in-memory Graph and mounted editor state that owns the user's immediate mutation and paint path. Typing, selection, pan, zoom, drag, resize, and other routine interactions must not await Profile capture, serialization, IPC, or disk confirmation.
- **Renderer Durability Queue**: The single renderer-side scheduling lane that coalesces routine changes into the newest Profile projection. It permits one native commit in flight and retains at most one newest queued projection; explicit checkpoints and lifecycle or Agent barriers flush it before their durability boundary. It is scheduling, not a second persistence authority.
- **Card Activation**: The visually neutral handoff from Passive to Live authority at the same position and size. Focus, programmatic selection, or a resolved direct interaction can begin activation; pointer hover remains presentation-only. For click-resolved oversized or Safety Cards, the shallow React Flow wrapper paints selection first without rerendering rich Card content; Live/editor work starts after that paint without losing the intended first click (ADR 0023). _Avoid_: Promotion.
- **Board Safety Representation**: The lightweight Board-wide visual representation that prevents blank regions while detailed Cards prepare. It does not own complete Card semantics or internal interactions (ADR 0023).
- **Image Rendition**: A purpose-sized, rebuildable form of an image asset used for a particular display or execution need. The saved image reference and content remain authoritative; renditions may be evicted, and compressed byte count is accounting rather than runtime authority (ADR 0024).
- **Mod**: A kind-specific thinking instrument whose whole Card face controls and visualizes its state. It deterministically contributes one treatment followed by its value sentences to whatever it is connected to. A Mod is data, never code (ADR 0030).
- **Mod Kind**: One of the eleven engine-owned Mod shapes: slider, dial, count, switch, pad, select, order, filter, mixer, radar, or matrix. Each kind owns its state, face, default treatment, and sentence mechanics (ADR 0030).
- **Mod Template**: A Profile-owned, reusable Mod document. Stamping gives the Board a frozen, self-contained copy with fresh stable nested IDs and immutable source provenance; template edits never touch existing stamps (ADR 0030).
- **Mod Context**: The exact treatment and value sentences read from one Mod. Connected Mods appear in user order in one `MODS` block; repeated kinds each contribute their own context (ADR 0030).
- **Mod Library**: The Profile-owned store of built-in and user-saved Mod templates. Boards never depend on it because stamps are copies (ADR 0030).
- **Intent Signal (retired)**: The removed Hold / Probe / Test / Crystallize card badge and compiler directive. Its old fields and events are dropped at load; it has no replacement built-in Mod (ADR 0030).
- **Detail Band**: The viewport-derived level of detail shared by the board at one instant: **Reading** at zoom ≥ 0.325, **Overview** between 0.15 and 0.325, and **Map** at zoom ≤ 0.15 (ADR 0019). Visible-card occupancy can demote Reading; text length is uncapped and never changes the band. In the bounded Reading↔Overview crossfade, editable DOM card visuals and Overview canvas bodies use complementary opacity until the DOM visual reaches zero; the Map↔Overview crossfade remains canvas-only.
- **Uniform Across the Screen at One Instant**: Every card uses the representation selected by the current detail band; it does not mean every screen-space label is visible, because label priority and collision intentionally vary by card.
- **Gesture Participant Set**: The bounded set of 0–2 lightweight or invisible Card representatives currently needed by hover/proximity transition, drag, resize, or connect work. It is separate from Live Card ownership: hover never creates a Live owner, an already-resident eligible gesture may retain one, and an oversized or Safety Card's pointer travel remains geometry-only (ADR 0020, ADR 0023).
- **Label Layer**: The screen-space canvas overlay that keeps selected, hovered, landmark, and eligible card names readable while resolving priority, collision, and frame caps independently from board-space shapes.
- **Landmark**: A structural anchor — currently a group or title card — whose label is eligible even in Map and wins ordinary label collision.
- **Connection**: A directed relationship between cards. Connections carry meaning through strength, polarity, and role.
- **Connection Strength**: How strongly a connected card shapes the consumer: **Direct** (solid line — build on this as primary material) or **Light** (dotted line — let it color the result lightly). Stored as `strong`/`weak`.
- **Avoid Connection**: A negative connection meaning "already explored — steer away and go somewhere structurally different," optionally with a one-line reason why the path died. Not a hard constraint: hard requirements are ordinary connected notes (ADR 0018). The stored polarity value remains `pushesAgainst`; the user-facing word is **Avoid** (its opposite is **Helps**).
- **Context Contract**: A card kind's one-place declaration of its connection behavior — whether it consumes context, what it contributes, whether walks pass through it, its connection defaults, and its presentation (`src/graph/contextContracts.ts`, ADR 0017). New card kinds plug into connections by writing a contract, not by editing traversal or compiler internals.
- **Agentic Run**: A Run in which the model may call tools rather than answering from the compiled instruction alone. Requested by the globe on an Ask AI Card, off by default. Who executes the tools is decided by the key, not the concept: with a Linkup key on OpenRouter, Eido runs the tool loop itself (ADR 0036); without one, the provider executes its server tools inside one completion (ADR 0033); a local harness owns its own tools and its own loop either way. It is an ordinary Run in every other respect, and it is unrelated to the Agent Gateway. _Avoid_: "agent mode", bare "agent".
- **Reach**: A Run's access to web search, page retrieval, and research. When a person supplies the optional Linkup key, Eido uses `src/brain/linkup.ts` to execute the tools (ADR 0037). Otherwise the AI provider owns any search it supports. Link previews use a separate keyless path for public page metadata. User-facing copy says "web mode" or "research mode", lowercase.
- **Reach Mode**: How much of the web one Ask AI Card's runs may touch. The globe in the Card foot cycles the three states, Off, Web mode, Research mode, and its tooltip names the state it is in, never the press that would leave it. The mode rides in `card.meta`, so a Board saved here opens in older builds with its reach intact (ADR 0037).
- **Web Mode**: The globe's ordinary armed state, in which the model can search and read pages. A supplied Linkup key lets Eido make each lookup and record its trail. Without one, a supplied OpenRouter key can use OpenRouter's supported web search. Eido provides no managed relay, key, or credit. Never priced on the Card.
- **Research Mode**: The globe's third state, available only while the person has supplied a Linkup key. Without that key, its control and function are disabled; a failed key has no managed fallback. The model may hand one whole investigation to the research endpoint, which runs for minutes on the vendor's servers. A submitted job cannot be stopped or refunded, so the first Run press on a research-armed Card is held while the Card says exactly that (ADR 0037). The job id is written into `card.meta` the moment the vendor acknowledges it, so a quit cannot lose the handle to work already paid for.
- **Search Depth**: How hard one lookup may work: `fast`, `standard`, or `deep` for search, plus mode and reasoning depth for research. The model chooses depth per call, from tool declarations and a travelling brief that carry the vendor's own selection rules; the user never does. A Card-face depth control was built and removed the same day (ADR 0037).
- **Tool Step**: One thing the model did during an Agentic Run: a search, a page read, a research job, a lookup that failed, or its own thinking between lookups. Steps stream onto the result Card while the run happens and are kept with the produced version, so an answer can always be traced to what it read. Each trail row is pressable across its whole line and opens to the full step; a read row's address lives inside its opened row, because one line cannot both open a page and open itself. The step vocabulary is open (ADR 0035), and the trail records Eido's own calls only: a deep search or a research job iterates on the vendor's side without reporting steps (ADR 0036).
- **Wire Record**: An opt-in, device-local, in-memory account of what a run sent on the wire: each request with its declared tools, each tool call with its arguments, each result's duration and size, each failure's kind, and never a header, credential, or response body. Lives in Settings under Board Info (#968) and dies with the tab; nothing reaches the Profile.
- **Link Preview**: A preview of a public URL attached to a Note. It can include the title, description, thumbnail, and favicon. A fetch failure leaves the link usable. Older Notes with page text and a saved source address retain that content and provenance.
- **Output**: The generated result record attached to a result-like card.
- **Output Version**: One generated version inside an output. Versions are kept so the user can choose, compare, and trace results.
- **Follow-up**: A question-and-answer thread on one version of a result card. Answers come from the original run's frozen context, never the live board. The thread travels with the card: when the result feeds another card, downstream context is the chosen version's answer plus its thread, and thread changes flip the source-changed badge. A reply can be turned into a Note.
- **Run**: A record of an AI execution: model, inputs, mods, compiled instruction, status, produced version, and—when delegated—trusted Agent attribution.
- **Recommended Model Catalog**: The editable starter list of OpenRouter models shipped with each Eido release. It is a device-local convenience, not an allowlist. A person may edit the list or add any OpenRouter model by slug; the selected model may remain Idea-scoped.
- **Provider Route**: Content-blind evidence of which provider access executed a Run. New execution uses `byok`; historical `managed`, `hosted-free`, and `hosted-paid` evidence remains readable only for saved Profile compatibility and grants no execution access.
- **Plan**: An Execution Plan describes which steps will run over which cards (ADR 0011, ADR 0013). Eido has no commercial plans.
- **Bring Your Own Key (BYOK)**: Provider access using credentials supplied and funded by the person, stored only on their device outside the Profile. It requires no Eido account or service. Missing access prompts the person to add a key or configure their local tool; provider failure never falls back to Eido-funded access.
- **Intent Log Event**: A coarse, timestamped event that explains meaningful board changes for playback and provenance.
- **Undo**: Short, fast, user-facing reversal of the user's own recent interactions. Undo is bounded and should stay in memory for responsiveness. Agent commits are never on the user's undo path; agent work is reversed by ordinary editing, aided by attribution visibility.
- **Playback**: Durable reconstruction of the board over time from semantic events and checkpoints. Playback does not need every keystroke.
- **Timeline Projector**: The module that turns board state plus intent log events into a board projection at a selected time.
- **Graph Index**: The derived module (`src/graph/graphIndex.ts`, reached through the store's `graph()`) that provides fast card, connection, group, output, and run lookups without feature code scanning full arrays. It is rebuilt from Board state and is never a second source of truth.
- **Checkpoint**: A stored projection state at an event index, used to avoid replaying the whole timeline for every playback scrub.
- **Performance Fixture**: A deterministic synthetic board used to measure whether the app still feels fast at target scale.
- **Release**: A published, numbered build of Eido that a person can install. A Release is the unit updates move between; it is not a Git commit or a source tag.
- **Update Manifest**: The signed record of the current Release: its version, its per-platform artifacts, the versions Eido refuses to keep running, and the oldest version still allowed. It is the only thing an installed Eido trusts to learn a new Release exists (ADR 0032).
- **Update Posture**: How a platform responds when a person accepts an update: **in place**, where Eido installs the new Release itself, or **notify only**, where Eido sends the person to the download page (ADR 0032).
- **Blocked Version**: A Release named in the Update Manifest as unsafe to keep running. An installed Eido that finds itself blocked stops ordinary work and asks the person to move to a good Release. This is Eido's recall mechanism (ADR 0032).

## Performance Principles

- The canvas renders the graph. It should not become the graph database.
- Undo and playback have different retention rules and should not share the same memory strategy.
- Full-board work is acceptable for import, export, migration, and explicit checkpointing. It should not sit on typing, dragging, streaming, or animation-frame playback.
- The in-memory Graph and mounted editor are the hot interaction authority. Routine changes schedule one coalesced renderer durability queue, with a shared three-second post-paint quiet window for text and released geometry; explicit checkpoints and lifecycle or Agent barriers flush the newest exact state.
- A durable save may lag a local interaction by the quiet window, but it must never delay that interaction. The queue preserves one native commit in flight and one newest pending projection without changing SQLite/Profile authority.
- Future features should reuse shared graph indexes, timeline projection, command/event capture, and persistence rules instead of creating local history or lookup systems.
- tldraw is a reference project only. Eido is not migrating to the tldraw SDK or tldraw technology.
