Eido Scalability Pattern Matrix

Use this when directing agents. First name the scalability problem, then choose the architectural pattern.

Reference Scales Best At Core Move Tradeoff Eido Translation
tldraw Interactive editor state: many records, bindings, viewport changes, undo, migrations. Typed record store plus incremental derived indexes and centralized culling. Powerful editor machinery and commercial/source-available licensing concerns. Create shared graph/render derivations. Keep canvas as a projection of Board records.
Excalidraw Fast-feeling simple canvas rendering and low-friction drawing UX. Scene maps, static canvas, interactive overlay, visible element filtering, restore repair. Arrows are primarily visual elements, not semantic relationships. Borrow render discipline, not the relationship model. Eido edges stay semantic.
n8n Execution scalability: partial runs, waiting state, run data, provenance. Separate authored graph from execution state and keep source lineage on outputs. Workflow-builder density can overwhelm a thinking app. Output versions and AI runs need graph snapshots, context traces, and re-run semantics.
Neo4j Graph meaning: typed directed relationships with properties and traversals. Treat nodes and relationships as first-class property-bearing entities. Database and license complexity are too heavy for early local-first Eido. Use property-graph ideas in Eido's own data model and context compiler.
Penpot Product/system scale: browser app, backend, workers, pub/sub, exporters. Move expensive or operational work behind worker, backend, storage, or service boundaries. More infrastructure than an early local-first prototype should carry. Useful later for sync, collaboration, exports, background AI work, and team workspaces.

The Five Founder Questions

1. What is hot?

Typing, dragging, streaming, pan/zoom, and animation frames must not scan the whole Board.

2. What is truth?

The Board/property graph is truth. Canvas, compiler, playback, and exports are projections.

3. What is derived?

If many callers ask the same expensive question, create a shared index or projection.

4. What is retained?

Undo, playback, run records, output versions, and caches need different retention rules.

5. What proves it?

Every scale-sensitive feature needs a deterministic fixture, unit gate, or browser perf gate.

Agent Direction Template

Before implementing this feature, answer:
1. Which Board records does it read and write?
2. Is this on a hot path: typing, dragging, streaming, pan/zoom, or playback tick?
3. What shared index, scene projection, run record, or worker boundary should own the expensive part?
4. How does this preserve "one graph, three views"?
5. Which test or performance command proves it holds at the large Board target?
