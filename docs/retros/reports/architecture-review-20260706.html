1. One run lifecycle module (brain layer)

Strong in-process
brain/runEngine.ts:50-109 + 413-467 brain/conversationRunner.ts:65-93 brain/followUpRunner.ts:33-46

Problem — three run loops (Ask runs, Conversations, Follow-ups) each hand-roll the same lifecycle plumbing: a registry of active AbortControllers (three different map shapes for the same concept), an isRunCanceled check reimplemented twice with different run-status queries, and a plainError function that is byte-for-byte identical in all three files. A cancel-semantics bug must be fixed three times by hand.

Map<string, Set<AbortController>>                 // runEngine.ts
Map<string, AbortController>                     // conversationRunner.ts
Map<string, {controller, assistantMessageId}>    // followUpRunner.ts

Also: the two-pass Compaction protocol (compile with no summaries → generate cheap-model summaries → recompile) is written out longhand in both runEngine.ts:160-182 and conversationRunner.ts:160-196 — a comment in the second literally says "mirrors runCard's two passes": copy acknowledged, not reused.

Deletion test — deleting any one file disperses nothing; the complexity was never concentrated. Three deep-looking modules hiding one smeared shallow concept.

Solution — one runLifecycle module owning controller registries, cancel semantics, and error-to-plain-word translation; plus one compileUnderBudget function owning the two-pass Compaction protocol with the compile primitive injected. All three runners become thin callers.

  • Locality — cancel bugs get one home, one test surface
  • Leverage — the next runner kind inherits cancel/budget behavior for free
  • Testability — tests move from three mocked loops to one real interface

2. Start and settle a Run once (graph store)

Strong in-process
graph/store.ts:1938-2069 (beginRun) graph/store.ts:2071-2136 (beginGroupDigestRun) graph/store.ts:2452-2584 (beginConversationRun) graph/store.ts:2151-2280 + 2719-2796 (finish/fail/cancel ×2)

Problem — "start a run against a card, producing an Output Version" is one concept implemented three times: each begin* action independently finds-or-creates the result card — re-deriving inline the exact lookup the Graph Index already exposes as resultCardFor, a leverage point built this session and then bypassed — then appends the Output Version, assembles the RunRecord, builds the event triad, commits, pushes undo. Terminal transitions are six near-identical blocks (finishRun / failRun / cancelRun + conversation variants).

// result-card find-or-create — byte-for-byte at store.ts:1945 and :2459
// output/version append — identical at :1990, :2077, :2505
// adding contextBudget this session required touching multiple begin* sites

Solution — one internal startRun(sourceCardId, kind, fields) helper owning result-card find-or-create (via the Graph Index), version append, and event assembly; one settleRun(runId, status) helper for the six terminal blocks. The three public actions stay but become thin.

  • Leverage — the next run kind or RunRecord field is one edit
  • Locality — provenance invariants get one place to test
  • Testability — every Run→version→event invariant checked once

3. A commit that knows about events (graph store)

Top recommendation Strong in-process
graph/store.ts — pervasive 67× commit() calls 41× makeEvent() calls 27× hand-rolled intentLog spreads

Problem — every mutating action re-derives the "append Intent Log Events inside a commit" ritual by hand. The concept has no name and no single location — a guarded-vs-unguarded mistake must be hunted call site by call site. This is the missing seam the roadmap already wants: the reviewed Graph Index design (context-layer.md) needs commit() to emit BoardChange records, and issue #154 (command contracts — the only open issue) is blocked on exactly that.

intentLog: [...s.intentLog, event]                       // unconditional
intentLog: event ? [...s.intentLog, event] : s.intentLog  // event-guarded
intentLog: events.length ? [...s.intentLog, ...events] : s.intentLog // length-guarded
Deletion test — nothing to delete; the behavior is smeared so thin no module holds it. That absence is the finding. The change funnel exists (one commit()) but events ride around it, not through it.

Solution — extend commit(updater, events?) so event append happens once inside the funnel. Every action passes its events instead of splicing the log. BoardChange emission then has a natural birthplace: the same call already sees what changed.

ⓘ

Aligns with ADR 0001 (event log as long-term source) and the reviewed Graph Index design; prerequisite for parked issue #154.

  • Leverage — one primitive serving ~25 actions and the doorway to Tier-2 incremental indexes, Playback slices, and issue #154
  • Locality — event-append correctness becomes one function, one test
  • Highest leverage of the set — it unblocks the only remaining open issue

4. One constructor for the board projection (canvas↔graph seam)

Strong (small) in-process
canvas/graphSelectors.ts:70-79 (boardOf) canvas/ChainPreview.tsx:39-42 canvas/ContextPeek.tsx:21-24 +8 sites app-wide with sentinel updatedAt:''

Problem — the SavedBoard projection ({version:1, cards, connections, outputs, runs, updatedAt:''}) is hand-assembled as a literal at every seam crossing. The named constructor exists (boardOf) but two UI modules re-literal it instead. If SavedBoard grows a required field, three-plus sites need matching edits and nothing forces it. Related: save.ts emptyBoard() and store.ts normalizeBoardForRuntime() are two independent partial-defaulting functions for the same type — emptyBoard's output isn't a valid runtime board until a second pass elsewhere backfills it.

Deletion test — deleting boardOf today breaks nothing — the symptom itself: the abstraction exists but has no leverage.

Solution — export one boardOf constructor and one board normalizer; every hand-rolled literal calls it.

  • Locality — the SavedBoard shape has one home
  • the sentinel updatedAt:'' gets one honest home
  • Testability — trivially testable in isolation

6. Name the LOD sub-policies (canvas scene)

Worth exploring in-process
canvas/boardScene.ts:107-294 (createBoardScene) boardScene.test.ts (13 tests, all whole-scene)

Problem — the scene planner derives ~19 interacting flags in one 190-line function. It passes the deletion test — deleting it would disperse LOD policy back into Board.tsx as ad-hoc conditionals — the module earns its existence. But internally the policy has no named parts, so every test constructs a full scene and asserts emergent properties, and this session's #167 regression came precisely from misreading the interaction of two flags (settled vs moving suppression). The fix required a comment block to explain two constraints one flag now encodes.

Deletion test — passes (deep) — friction is internal organization, not existence.

Solution — split into named, independently testable sub-policies (aperture state, board-scale class, detail budget, suppression) that createBoardScene composes.

⚠

This area is guarded by the dense-board perf gates and was stabilized this session (#150 / #158 / #167). Refactor only with the gates run locally before and after.

  • Locality — the #167-style settled-vs-moving rule becomes a two-case unit test, not a browser-perf-gate archaeology dig
  • perf gates stay as integration backstops, not the only net
