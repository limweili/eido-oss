Area 1 — Work delivered

The epic moved from an approved visual proposal to an app-wide authority, then composed that authority with the production renderer and storage line before one identity-preserving promotion to main.

Delivered versus intentionally excluded

Delivered

  • Light, Dark, and Match-system authority; semantic tokens; typography; local fonts; reduced motion.
  • Shared controls, fields, buttons, badges, dialogs, tooltips, overlays, focus ownership, and responsive chrome.
  • Card identity, canvas painter/cache parity, connections, Mods, Highlights, playback, AI/version surfaces, and context rows.
  • Production P/S/L rich-Card rendering, long Cards, image renditions/lifecycle, Board Search, accessibility continuity, and save/export compatibility.
  • Static design drift authority, exact Required, macOS/Windows native proof, bundle budget, and main release artifact.

Not delivered

  • Migration or visual preservation of Card colours in old save files; identity is forward-only.
  • Storage-version changes, private-save validation, or any .multy state.
  • #471 packaged-runtime certification, which remains independently owned.
  • Real-user adoption, usability research, sentiment, retention, or business metrics.
  • A promise that every future screen is automatically coherent; the authority and drift checks make that enforceable, not inevitable.

Selected decision or architecture

DECIDED The design system is a set of named semantic authorities, not a palette copied into consumers. Components ask for roles such as ink, line, field, badge, overlay, or Card identity; shared modules decide the concrete appearance and interaction contract. The terminal integration merged current main into the design line once, preserved the reviewed tree, and promoted that ancestry intact.

Rejected approaches were replaying or rebasing 59 design commits one by one; preserving raw old-main CSS beside the new system; creating a second Search surface; migrating legacy save colours; and rebuilding proof for unchanged seams after every lineage change. The trade-off is stronger central ownership and less local styling freedom in exchange for coherence, drift resistance, and cheaper future change.

Area 2 — Technical teaching

Technical story in one minute: before #491, many screens each carried a small private design system. Now a component names the role it needs, a shared authority supplies appearance and interaction, the canvas painter uses the same theme inputs, and focused tests protect the owner rather than copying assertions into every consumer.

How it works

Mechanism: semantic tokens and typography roles flow into shared primitives, overlays, Card identities, and painter rules; consumer components compose them. Trade-off: local components have less freedom to invent raw values. Product meaning: Light/Dark behavior, focus, hierarchy, and canvas/DOM identity can change coherently. Validation gate: static drift checks and focused owner tests run inside exact Required, with causal browser or perceptual review only where a shared seam cannot answer the question.

Friction, bottlenecks, and how they were unblocked

The suspected risk was that a large visual migration needed broad proof everywhere. The actual constraint was review and validation volume. Computer Use became an acceptance oracle, Playwright coverage grew horizontally, issue clauses encouraged per-theme/per-viewport matrices, and replacement CI runs were watched even when commit and tree identity were unchanged. #503 later removed 481 lines from one browser matrix while retaining the two distinct causal journeys. Host-explainable path aliases and optional canaries were initially noisy but did not represent product defects.

The unblock was to concentrate proof: static review for semantic authority, owner tests for shared behavior, causal browser journeys only for timing/focus/geometry, one short perceptual review at meaningful composition, and exact Required at the landing boundary. When a checker wanted a v2 or evidence work outweighed product work, the team stopped and resliced.

Founder interventions

The founder correctly identified Computer Use, Playwright, and excessive test creation as the bottleneck, then clarified that even Playwright should not be treated as a universal oracle. That intervention immediately changed lane contracts, reduced evidence breadth, and made visual review perceptual rather than behavioral. The cost was a mid-epic process reset: active plans, skills, and assumptions had to be re-derived after PRs #541/#542 and ADR 0028. The reset was worth doing, but the same framing at epic kickoff would have avoided churn and contradictory issue contracts.

Agent and team accountability

The delivery team should have recognized earlier that proof volume, not defect escape rate, was dominating cycle time. It overbuilt matrices, allowed a coordination registry to accumulate sediment, let one reviewer run without a bounded verdict contract, and initially treated replacement runs as new evidence. Those were orchestration decisions, not unavoidable tool limitations. The team improved when it separated causal, perceptual, static, and provider-state questions and assigned each to one authoritative proof.

Keep / Stop / Start / Change

Keep / Start

  • Keep foundations before consumers, continuous serial landing, exact tree identity, and a retro separate from mutable coordination.
  • Keep Standards and Spec review independent at meaningful stable boundaries.
  • Start every epic with an evidence map: claim, owner, invalidation boundary, and stop rule.
  • Start issue-contract review before implementation when old clauses imply exhaustive matrices.
  • Start a small post-release product measure when user or business impact matters.

Stop / Change

  • Stop per-consumer proof for unchanged shared roles and stop using visual tools for timing or gesture truth.
  • Stop unbounded reviewers; no verdict means incomplete, not approval.
  • Stop repairing tests that require deliberately retired behavior.
  • Change draft-to-ready workflow triggers or merge policy so identical heads do not pay for duplicate Required/native runs.
  • Change recovery notes to point at live GitHub/Git/CI authority instead of duplicating task state.

Decisions to make before the next epic

  1. Acceptance contracts: which per-card, per-theme, and per-viewport clauses should be removed from the default issue template?
  2. Review placement: should Standards review happen immediately after shared-seam shape stabilizes, before large consumer evidence?
  3. Visual review: which intermediate heads deserve perceptual review, and what belongs only at terminal integration?
  4. CI triggers: can draft-to-ready replacement runs be removed without weakening exact-head truth or branch protection?
  5. Recovery state: what is the smallest committed handoff after compaction when GitHub, Git, and CI are authoritative?
  6. Process ownership: which lessons belong in system-agnostic skills, Eido's release profile, or this one-off retro?
Recommended decision order: settle acceptance contracts and CI duplication first; both directly reduce the next epic's proof volume. Then place Standards and visual review around the resulting smaller delivery slices.
