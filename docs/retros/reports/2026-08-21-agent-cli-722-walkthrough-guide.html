Completion review · issue #722

The CLI is an outside control surface. Eido still owns its AI runs.

A caller and an AI provider can look like the same thing from the terminal. If they are confused, the founder can grant the wrong authority or misread the walkthrough evidence only after a real Profile or paid Run is involved. This guide separates them before either boundary is crossed.

Read this first

If you remember only one thing, remember the arrows: outside agent → Eido CLI → Eido Profile. Eido then runs its own Ask AI card.

02

The product in one page

What the `eido` command lets an agent do

Think of the CLI as a narrow, local remote control for a user’s open Eido Profile. It is deliberately more limited than a database or filesystem handle.

It is

A safe way to work with a Board

  • Discover the surface: status, capabilities, and help.
  • Read a bounded area using a Card Deep Link.
  • Preview, then apply one change at a time.
  • See placement, creator attribution, search, and changes.
  • Ask Eido to submit a live Run while the app is open.
It is not

A back door into the Profile

  • No Profile path, raw SQL, database handle, or generic patch.
  • No provider key or credential access for the outside agent.
  • No remote server and no headless AI execution.
  • No direct editing of AI results or transcripts.
A simple example

Agent asks: “Put a note beside this card.”

Eido checks the current revision, shows a dry-run preview, and only then applies the move.

Why this matters

Without revision and credential boundaries, the founder could discover a wrong change or exposed secret only after it reaches a real Profile. The CLI refuses that work before apply.

Full CLI feature map

The command surface is bigger than the original walkthrough summary

This lookup lists every user-facing feature family in the CLI help and runbook, with the job each one does. PR #1193 carries a separate set of follow-up refinements and must pass its own merge and certification checks.

Branch finding

PR #1193 adds or sharpens v5 behavior around Result inspection, Mod identity, atomic grouping, Ask and Conversation variations, credential failures, and disposable review mode. The feature map below explains the contract; it does not claim that separate PR has passed its landing gate.

CLI feature families, their jobs, and the commands or limits that define each one.
Feature family What it lets the agent do Commands and limits
1. Start and understand Find the installed surface and its bounds before acting. eido, --help, describe, status, capabilities, and raw batch. --pretty changes presentation only; client and session flags label attribution.
2. Read the Board Inspect one bounded, revision-pinned slice instead of streaming the whole Profile. idea list, graph query, graph neighbors, graph bounds, record get, result inspect, Mod inspection, and changes. Card Deep Links carry authoritative Idea and Card identity.
3. Create and edit Make explicit Board changes across Ideas, Cards, identity, placement, and Groups. idea create|activate, card create|update|delete, ask model, card identity, cards arrange|layer, and atomic group add|remove.
4. Connect and curate Keep Connection meaning, placement, and selected Results explicit. connection create|update-meaning|delete, --connect-from, --near, and result choose|accept|unaccept. The commands create or remove Connections, never generic edges.
5. Mods and templates Inspect and change inert visual controls without exposing executable content. mod create|configure|delete|connect|stamp plus template list, inspect, create, configure, and delete. A Mod connects to an Ask or Conversation through a helps Connection. Its exact versioned spec stays bounded.
6. Delegate an Eido Run Ask the live app to execute its own Ask AI or Conversation engine and return bounded references. run CARD, --variations N for 1–8 outputs, run status, run read, then record get. The CLI receives no provider key; app-closed execution fails live-app-required.
7. Safety on every write Keep mutations reviewable, attributable, bounded, and safe to retry exactly. Every write pins --expected-revision and chooses one of --dry-run or --apply. Idempotency, cursors, byte caps, exit categories, and one-way surface-v5 compatibility fail closed.
04

The remaining human test

#722 is a founder walkthrough, not another unit-test ticket

The code and package checks are already landed. This last issue asks: does the whole flow feel understandable, visible, undoable, and safe when a fresh person uses the real packaged app?

  1. Prepare a disposable place

    Use a fresh macOS graphical account and the certified DMG. Confirm the Eido data root is empty before launch. Pass when: no personal Profile, keychain, browser, or provider state can be touched.

  2. Give the agent two synthetic links

    Create a small, fake Board story and copy only its Card Deep Links. Pass when: the agent starts with zero context and no local paths, tokens, or real content.

  3. Let the agent discover and read

    Run bare eido, then status/capabilities and one bounded graph read around the anchor card. Pass when: a new agent can understand the surface without tribal knowledge.

  4. Preview and apply a thought

    Ask for a note near the anchor. Check the dry-run, apply it, and watch the live Board update. Pass when: position, agent attribution, undo, and retry all feel obvious.

  5. Prove safety and adoption

    Try an old revision and confirm it is refused. Find the card by Agent creator, edit it in the GUI, and confirm user attribution remains distinct. Pass when: stale work cannot create a surprise card.

  6. Run one real Eido Run

    Use a disposable provider identity and a low-cost model. Submit an Ask AI card through Eido, read bounded status/artifact metadata, then confirm app-closed and cap failures are clear. Pass when: Eido owns the run and the agent can observe it without seeing secrets.

  7. Write the short transcript

    Record revisions, transport, placement, findability, adoption, Run status, and friction; never prompt output, paths, or keys. Pass when: a sanitized follow-up PR captures what the founder actually felt.

Current gate

The packaged DMG is eligible. The real-provider walkthrough has not been run because the disposable OS account, disposable provider identity, spend ceiling, and founder felt-use authorization are not yet supplied.
