Eido Codebase Simplification — Founder Review

Executive summary

Eido is materially simpler without changing what users can do. Five bounded review passes landed sixteen risk-ranked refactors: 542 additions and 39,251 deletions across 102 changed-file entries, or 38,709 net lines removed, plus one exact 2,084,960-byte binary duplicate. The fourth and fifth passes added four landed changes and routed fifteen overlapping opportunities back to their active owners instead of creating competing work.

What changed now

The terminally rejected content-visibility architecture is no longer executable. Canvas, Graph Index, graph-store, brain, overlays, theme/motion, and shared-copy modules now publish less incidental surface or own compatible mechanics once. The last two passes put connection admission behind the indexed graph seam, shared an overlay selector and media-query lifecycle, and deleted twenty unreachable copy entries.

What users or the business receive later

This is not a new feature. The expected benefit is faster, safer future delivery because agents and engineers have fewer paths, flags, snapshots, workflows, and duplicated policies to understand. That productivity effect has not yet been measured.

Delivered versus intentionally excluded

Delivered

  • Retired the rejected content-visibility runtime, evidence, CSS, workflow, and policy surface.
  • Moved remaining live lookups and connection admission onto the existing indexed graph authority.
  • Narrowed passive residency and BoardScene to runtime-consumed values.
  • Centralized compatible Connection, Version, clone, Highlight deletion, overlay focusability, and media-query lifecycle mechanics.

Intentionally excluded or retained

  • Cached-passive/rich-Card performance, persistence/lifecycle, provenance/lineage, image migration, and release work already owned by open issues or PRs.
  • Renderer routing, residency hysteresis, runner settlement, cancellation, cache leases, and Electron/SQLite security boundaries that encode real variation or assurance.
  • Fourth/fifth-pass persistence, native-proof, workflow, rich-Card, Mod, follow-up, canvas-interaction, and test-harness opportunities were documented for their live owners rather than patched here.
  • Earlier semantic undo, Version provenance, design mirrors, image adaptation, skill mirrors, timeline direction, and digest compatibility likewise remain with their named owners.

Selected decision or architecture

The governing choice was deletion and locality, not abstraction for its own sake. The program first asked what each area exists to achieve, then applied a deletion test: remove a losing, unreachable, or byte-identical path entirely; otherwise put repeated compatible mechanics behind one narrow seam while keeping caller-specific policy visible. #640 shows the standard in practice: its first shared planner added about eighteen production lines and scanned raw arrays on a connect-drag hot path, so review held it. The final planner accepts only three indexed graph reads, returns IDs rather than whole Cards, and is net −1 production line. Active ownership was also a qualification gate, so obvious simplifications inside current work became source-grounded comments rather than competing tickets.

Area 2 — Technical teaching

Technical story in one minute: good refactoring removes knowledge. The largest changes deleted an option Eido had rejected, a generated artifact with no remaining owner, and an exact binary mirror; smaller changes gave compatible policy one local authority. The most important late correction was refusing to centralize connection rules through raw-array scans: both preview and mutation now ask the cached graph index for one plan, while mutation side effects remain in the store. Public behavior stayed fixed because event order, persistence, security, rendering policy, and user-facing projections stayed at their authoritative seams.

How it works

Eido is one saved graph projected as Canvas, semantic context, and execution. The review protected that authority while looking for leaked implementation detail. Content visibility was a complete losing architecture—runtime store, DOM vocabulary, CSS, evidence builders, reports, and CI—so the elegant solution was contraction, not another switch. Later passes applied the same deletion test to an ownerless snapshot, duplicate binary, and dead copy. For connection creation, planConnectionAddition consumes only cardById, outgoingConnections, and resultCardFor from the cached BoardGraphIndex; it returns null, a direct plan, or a through-Result plan. Canvas uses that answer for preview validity. The graph store uses the same answer but still owns ID generation, Result placement, mutation, commits, intent events, undo/redo, and pulses. Overlay focusability and media-query lifecycle follow the same shape: one private mechanism, while provider filtering and theme/motion semantic fallbacks remain local.

Friction, bottlenecks, and how they were unblocked

The live retro caught friction as it happened: isolated worktrees repeatedly lacked the pinned dependency tree; graph metrics sorted numeric strings lexicographically; GitHub connector reads/mutations intermittently returned false 404s; and the canonical budget reader timed out on serial provider work. A complete twelve-reader equivalent instead validated 1,296 current-month runs, 1,365 billable jobs, 2,986 rounded minutes, and conservative gross spend of $20.428 before merging. In the final passes, literal tracker search missed #466's semantic network-egress ownership, the first #637 planner failed both the deletion and indexed-hot-path tests, a stale focused-test path briefly undercounted proof, a larger reset-helper inventory was misread as a new owner, and the first #642 worktree command used a directory that did not yet exist. Each was recorded immediately, corrected without hiding the failed approach, and re-proved at the affected seam. The browser client was not retried for this content-only closeout after its earlier bootstrap failed before page load with Cannot redefine property: process. The unchanged report shell retains its prior interactive proof; this revision passed fresh static/comment-contract validation and the standalone file opened successfully.

Founder interventions

The founder's successive constraints materially improved the work: ticket every unowned opportunity, keep a live retro, exclude pre-owned work, rank the top 50%, declare when exploration is done, protect rich-Card performance explicitly, and prefer a precise comment over a competing refactor ticket inside active work. Those rules prevented collisions across persistence, native proof, rich-Card, timeline, agent-interface, provenance, image, undo, design, workflow, Mod, and test-harness work. The request to keep looking produced four more safe changes, but the risk-ranked stop rule kept the continuation from becoming endless polish.

Agent and team accountability

The team should have treated ADR 0023's terminal selection as a contraction event before this program; leaving the losing experiment executable created most of the eventual cleanup. In the continuation, the orchestrator should have run semantic boundary ownership before publishing #636, challenged #637's whole-patch size and hot-path interface before its first draft, resolved test paths from the live tree, and compared later findings with the program's own semantic ledger before calling them new.
