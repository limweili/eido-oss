Epic #410 — how a rendering decision grew a 14,000-line evidence product

The chain of events, in plain language: the work machine (a managed Mac) could not launch the browser needed for performance measurements, and background security software polluted all timing numbers. So measurement moved to rented cloud machines. Cloud machines are shared and noisy, so agents built machinery to prove each measurement was trustworthy — process guards, cleanliness checks, tamper-evident evidence formats. Reviews then (correctly) found bugs in that machinery, which produced more machinery. Twelve versions of the evidence format later, the system reached self-parody: a cloud run failed its own "machine must be idle" check 34 milliseconds after finishing its own 19-second, 339-case test preflight — the gate rejected the load that the gate itself had created. That was the run you challenged.

Classification of ~300 substantive friction entries: ~45% apparatus defects (the harness, fixtures, validators, and guards breaking), ~38% proof/ceremony overhead (re-proving after every branch movement, review rounds on evidence formats, environment fights), ~15–18% genuine product catches. And of the genuine catches, most came from adversarial review, not from the accumulated test cases.

Open the forensic detail for #410
  • The waste, concretely: 11 cloud measurement dispatches, all failed closed, none produced accepted evidence; #404 duplicated ~1,248 lines of benchmark choreography rather than sharing a seam; every head change reset all gates including finished reviews, so even harness-only commits re-triggered full re-proof.
  • Apparatus fighting the product: the frozen baseline's readiness check assumed all 131 cards stay in the page — structurally opposed to the very change being tested; a source-location guard forced a clean refactor to reorganize around the guard; a correct workflow change was failed by a stale contract test expecting the literal old text.
  • Genuine saves worth protecting: the deep-scroll veto that correctly killed the #404 candidate; the real-click retarget veto; a default-off feature flag that still attached live runtime work; a review that caught fabricated "0 ms" evidence claims; four real main-branch regressions caught by the browser canary.
  • After the trim: "one current-head gate, one serial merge, and one exact-main release object per meaningful slice were sufficient; repeated local/browser/performance proof would not have changed these decisions" (#407–#409 closeout).

The five root causes

  1. No counter-pressure on evidence. Every red produced more machinery; nothing asked "would more proof change the decision?" The loop only ended by founder intervention. This is the root; the other four are amplifiers.
  2. Fail-closed absolutism plus proof-reset rules. "Absence is never green" combined with "any branch movement resets everything" multiplied re-proof. The fix (reuse exact proof until a relevant change invalidates it) is now adopted but lives only in skill files.
  3. Hostile hosts made apparatus the work. A Mac that can't launch a browser, security software that poisons timing, and a Windows machine that can't run the repo's own gates. Agents kept re-fighting the hosts instead of declaring one authoritative environment per epic.
  4. Unbounded review economics on shared state. Expensive reviews bound to exact branch positions, on branches multiple writers moved, with no time/dollar budget and no formal "incomplete" outcome — so paid work was silently raced and invalidated.
  5. Instructions treated as truth over principles. Stale tracker edges routed the critical path; stale acceptance text nearly forced fake work; retired coordination ceremony (Multy) held authority long after its environment died; and there is no testing ADR to re-derive from — the philosophy exists only in skill files an agent may never load.

The SQLite fear, assessed

You are right that the current test estate contains old-architecture assumptions that will fight the SQLite migration — it already happened twice in miniature (the Intent Log text guard, the stale #521 acceptance text). But the retros also contain the antidote, adopted as rules near the end of #520: implementation evidence may amend a stale spec (the agent owns the adjustment and escalates only consequential choices), and unrelated breakage becomes a truthful non-blocking issue instead of scope creep. The practical translation for the SQLite epic: before work starts, the orchestrator should produce a short founder-visible list of old save-file tests and SOP sections that the new architecture deliberately retires, retire them in one visible decision, and protect only the seams that survive the migration (data safety, import/export truth, the save-file SOP's privacy rules). The genuinely dangerous part of #520 was not old tests — it was the epic spending its energy off-path. That is an orchestration fix, covered next.

Area 2 — How the self-reinforcing evidence loop worked

Technical story in one minute: proof has a property product code doesn't: when proof fails, the reflex is to build more proof. A noisy machine makes a measurement look unreliable → agents build machinery to certify the measurement → a reviewer finds bugs in the machinery (reviewers are good at this) → agents fix and extend the machinery → the machinery itself now generates load, files, and branch movement that trip the next check. Every step is locally reasonable; the sum is a second product. The only exit is a question asked from outside the loop: does any of this still change what we ship? In #410 you were the one who asked it. The fixes in this report make the system ask it automatically.

The loop, step by step

  1. Trigger: the environment can't produce a trustworthy signal (Mac can't launch the browser; security agents poison timing; Windows can't run the gates).
  2. Relocation: proof moves somewhere else (cloud runners), which introduces a new trust problem (shared, noisy machines).
  3. Fortification: machinery is built to make relocated proof trustworthy — guards, cleanliness checks, tamper-evident formats, process ownership ledgers.
  4. Ratchet: adversarial review audits the machinery and correctly finds it fail-open; each finding widens the machinery (evidence format v1→v12; guard v1→v4). No finding is ever "this evidence no longer matters."
  5. Self-collision: the machinery's own weight trips its own checks — the run that failed its idle-machine gate 34 ms after running its own 339 tests; the load ceiling that mathematically rejected every valid sample of its own workload.
  6. Exit (manual, this time): founder asks the decision-value question; 205 cases become 23; ~14,000 lines leave the blocking path; the decision lands in hours using evidence that had existed for days.

The loop as a picture

The inner cycle (certify → review → extend → self-collide) can spin indefinitely because every iteration is locally justified. The green exit is a judgment call, which is why it must be a standing principle rather than a lucky intervention.

  • Review dollar figures cover completed verdicts only; failed attempts, a ~12-hour unobserved reviewer, and orchestration wall-clock are real but unquantified, so total ceremony cost is understated. Owner: Merge Captain fix (budgets + lifecycle watcher).

Epic Orchestration — right principles, no teeth

Role in what happened. The orchestrator is the only role with the whole map, so it owns the two biggest misses. First, it let evidence machinery grow lane by lane: each lane's extra validator or guard looked locally reasonable, and nothing at the system level compared harness effort to product effort. Second, in #520 it derived the critical path from tracker links instead of asking what technically blocks what — two days and the epic's costliest review went to another epic's renderer work. To its credit, the current skill (post-#541) already contains the right sentences: "evidence exists to reduce uncertainty about the goal," "stop and reslice when evidence machinery approaches the complexity of the change," and a source-precedence ladder that puts live reality above cached plans.

What to fix.

  • Turn the stop-rule into a tripwire with named triggers. Today "stop and reslice" is advice with no trigger, so it fired only when you intervened. Give the orchestrator explicit tripwire conditions it must act on without escalation: a lane's evidence diff outweighs its product diff; a second version of any validator/guard/harness is being built; a gate red is explainable by the environment rather than the code; proof is being rebuilt for a head that hasn't semantically changed. Action on trip: pause the lane, answer the decision-value question in one paragraph, reslice or delete.
  • Critical path by mechanism, not by tracker. Adopt #520's rule 149 into the skill: every blocking edge must name the direct technical mechanism by which A blocks B, verified against the code — tracker links are hypotheses.
  • One environment verdict and one known-debt inventory per epic. At kickoff, declare which host is authoritative for which evidence (for Eido today: hosted Linux CI for gates, full stop) and publish a short SHA-pinned list of known pre-existing failures. Three #520 lanes independently re-proved the same three inherited errors; that is pure waste the orchestrator can delete with one shared document.
  • Retire-list for architecture changes. When an epic deliberately changes architecture (SQLite), the Map step must produce the founder-visible list of tests/SOP sections the new architecture retires, so old tests are removed by one decision instead of fought lane by lane.

Merge Captain — sound contract, leaking economics

Role in what happened. The captain's core contract — reuse valid exact-head proof, don't repeat broad gates, scale proof to landing risk — is exactly the philosophy you want, and when it was actually applied (#405–#409 landing train) it worked beautifully: one gate, one serial merge, one release proof per slice. The leaks were operational. Its bundled gate scripts require bash and jq, which don't exist on the Windows host every #520 lane used, so every lane hand-reimplemented the gates — apparatus work the skill itself caused. And it had no cost model for review: verdicts costing $2.75–$6.26 and 17–48 minutes were bound to exact branch positions on branches that other writers kept moving, so a 48-minute review died mid-flight and a detached reviewer ran ~12 hours unobserved.

What to fix.

  • Per-review budgets and a formal INCOMPLETE outcome. Before dispatching an expensive review: a wall-clock and dollar cap, sized to the change. Overrun or transport failure returns INCOMPLETE — never PASS, never a silent retry. (#520 adopted this as rules 17/92; promote it from the retro into the skill.)
  • Single-writer lease on any branch under paid review. The three head-drift freezes and the invalidated 48-minute review all trace to multiple writers on one PR branch. Rule: while a review or landing is in flight, exactly one role may move that branch; everyone else queues.
  • Make the gates portable or stop pretending they're local. Either ship Node entry points for the mandatory gates (the repo already has precedent) or amend the profile to say plainly: on hosts that can't run them, hosted exact-head CI is the gate and local re-derivation is forbidden. The current middle ground — bash-only scripts plus "use a manual equivalent" — bought #520 dozens of hand-built gate reimplementations.
  • Prefer executable counterexamples over verdict prose. A paid review PASS missed two real blockers that cheap executable probes caught (#520 rule 175). The captain should weight falsifiable checks above reviewer confidence when they conflict, and may downgrade review depth where a probe exists.

DevOps Coach — the missing smoke detector

Role in what happened. Mostly absence. This is the one skill whose explicit job is to "classify the active constraint" and choose the single highest-leverage intervention — precisely what was needed when validation became a second product. It is well written (founder-hands-off, evidence-first, "test count alone is never a diagnosis"), but it is marked manual-only and was never invoked during either crisis. The system's designated loop-detector was switched off, so the loop-detection fell to your gut feeling.

What to fix.

  • Give it a cadence. Keep it manual-only in authority (it decides nothing without you) but standing in schedule: run at every epic kickoff and closeout, or weekly during an active epic. Its output is already founder-shaped: green/amber/red, one bottleneck, one decision, at most one founder action.
  • Add the harness-share metric to its checklist. One new constraint class it must always evaluate: what fraction of recent commits, open follow-ups, and lane effort is process/harness work versus product work? In #520 that number was ~100% infrastructure for two days — an unmissable alarm had anyone computed it.
  • Add "evidence yield" to its evidence set. Dollars and hours of review per accepted blocker, and gate runs per accepted evidence artifact. Eleven cloud dispatches for zero accepted evidence in #410 should page the coach, not the founder.

## Evidence philosophy

Tests, gates, reviews, and evidence are instruments for one question: would
more proof change what we do next? When the answer is no, land the work. Scale
proof to risk — irreversible actions, shared-state mutations, security and
external boundaries earn deep, adversarial evidence; routine reversible work
earns the cheapest authoritative check; nothing earns proof repeated for
ceremony. Prove a shared behavior once at its authoritative seam and reuse that
proof everywhere until a relevant change invalidates it. Prefer a few broad
tests at real product seams over many narrow ones pinned to internals: narrow
tests fossilize today's implementation and tax tomorrow's change. Tests serve
the product's direction, never the reverse — when architecture moves, tests and
spec text move with it; a test failing because behavior was intentionally
retired is a deletion, not a blocker, and implementation evidence may amend a
stale spec. Validation must never become a second product: when evidence
machinery rivals the change it validates, or a failing check says more about
the host than the code, stop building apparatus and shrink the question
instead. Every SOP, skill, and gate here is a means; when one demands effort
out of proportion to the risk at hand or contradicts observed reality,
re-derive intent from the ADRs and CONTEXT.md, act on the principle, and flag
the drift.
