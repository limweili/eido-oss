# ADR 0029: Electron Main Installs One Profile Authority

Status: accepted

## Context

ADR 0025 chose SQLite as the Friends Alpha Profile authority, but did not fix the production path, process ownership, renderer handoff, or local headless-access boundary. Leaving those choices to each transport would allow package branding to relocate data, synchronous SQLite to block Electron's UI loop, hydration races to discard renderer intent, or a second process to become an accidental writer.

## Decision

Electron main owns installation and trust for the packaged Profile. The product root is always `path.join(app.getPath('appData'), 'Eido')`, and the default database is `profiles/default/eido-profile.sqlite` beneath it; package name, application ID, and signing identity do not choose durable authority. After exact mode selection and before yielding to readiness or stdin, startup synchronously validates its installation, creates only that product root, and pins it as `userData`; invalid headless setup emits one generic contract failure and exits without waiting for input. GUI startup additionally requests the single-instance lock, while headless startup does not. Only the GUI primary may register the privileged `eido` scheme. After readiness, GUI startup installs the protocol/security boundary and starts its Profile utility. Headless request admission and readiness may complete in either order, but both must complete before an existing-only lease opens. The utility creates Profile descendants only for active GUI authority; it seeds or acquires ready or recovery-required authority before main loads a renderer. JSON/GUI package proofs may substitute one explicit disposable root. Ordinary runtime and the MCP entry remain fixed-path and accept no caller-selected root.

One Electron utility process is the only packaged process that opens the SQLite Profile and its sidecar/blob/recovery state. It owns the complete native service and serializes revision-affecting work through one authority queue; Electron main owns the typed utility proxy, exact `eido://app` frame/origin trust check, narrow versioned preload bridge, file-choice capabilities, and process lifecycle. The renderer never receives SQL, paths, owner credentials, Profile identity-setting authority, or a fallback to browser storage. A first run seeds the checked-in built-in Mod templates as immutable native template records so their stamp provenance exists at the first commit.

Hydration is an explicit apply/acknowledge/admit handoff. The host issues an epoch and authoritative revision; Electron main carries the fixed packaged session `intentActorId` (`eido-desktop-gui`) beside the `ProfileSnapshot`, and the packaged renderer pins it before applying state, acknowledging the exact `{ epoch, revision }` pair, or admitting the store. Every new packaged Intent event is stamped with that pinned actor. Native admission preserves the exact submitted Intent prefix, rejects any appended suffix whose actor differs from the hydrated `intentActorId`, and never rewrites actor attribution. Packaged mode neither reads nor writes actor identity through `localStorage`; the `eido-v3-actor-id` key remains an explicit browser-development mechanism only. The renderer installs the complete native state, or a safe three-way rebase of its complete renderer-owned delta, before acknowledgement. The rebase treats active selection, each Idea's metadata, every Board replacement (including non-active Boards), template changes, and pending Mod origins as one projection while detecting divergent overlap. Once the reconciled projection is applied, it becomes both the raw-renderer and authority rolling baseline before the acknowledgement gap, so a mutation observed during that gap is one new delta and cannot be replayed against the pre-lifecycle base. Exact acknowledgement clears both adapter admission fences—acknowledgement-pending and recovery-required—before synchronous store admission. A synchronous ready observer is accepted for both startup and successful recovery. Unsafe reconciliation or acknowledgement/admission failure is sticky terminal; it cannot discard work, select another authority, or reopen recovery.

The renderer keeps routine interaction ahead of durability. The in-memory Graph and mounted editor apply text, selection, pan, zoom, drag, and resize immediately; they do not await whole-Profile capture, serialization, IPC, or native confirmation. Packaged text edits and released geometry share one 3,000 ms post-paint quiet window, while browser-development persistence uses the same latest-source debounce. The existing renderer persistence queue permits one native commit in flight and retains only the newest queued projection. Explicit checkpoints, lifecycle transitions, Agent barriers, and shutdown flush routine work and require exact durable revision confirmation. This is a scheduling policy over the existing authoritative projection, not a second store, delta format, or SQLite authority.

Normal shutdown is certified by the renderer's exact authoritative `{ nativeGeneration, revision }` checkpoint. Main stops admission, flushes through the installed authority queue, requires the native pair to match, and requests close. The utility drains admitted work, closes the Profile, releases its sidecar as the final persistence resource, acknowledges close, and is then joined by main. Recovery-only shutdown may omit the pair because it admitted no mutable renderer. On readiness, protocol, checkpoint, close, or utility-exit uncertainty, main reports terminal failure and attempts bounded forced termination and join before the packaged process exits; a failed bounded join cannot be represented as a clean shutdown.

The installation also owns trusted `cli` and `mcp` variants of one lazy, parameterless, existing-only headless lease factory for in-process callers. Each opens the same fixed path in an `exclusive-headless-owner` utility without seeding or creating a missing Profile, exposes the installed bounded Gateway operations and allowlisted command batch, and drains, closes, and joins on release. The private initialization payload requires one trusted transport and the utility binds it for the lifetime of that owner; request JSON cannot select transport, Profile path, or credentials. Same-key cross-transport replay therefore fails without a duplicate effect while same-transport replay retains its durable semantics. Absence, contention, future incompatibility, and recovery remain typed outcomes.

One transport-neutral Gateway session sits above that factory. Its synchronous `describe` projects the installed operations from static descriptors without acquiring authority. The first valid headless `invoke` single-flights and retains one existing-only lease, and `close` first stops new admission, then drains accepted work before closing that service. The exact packaged `--eido-profile-json` mode uses the `cli` factory after pure request admission and Electron readiness, invokes once through this session while preserving the caller's request ID, and joins close before output. ADR 0031 adds a separate app-owned local-IPC route to the already-active GUI owner; it does not add another SQLite owner or path resolver.

The exact packaged `--eido-profile-mcp` mode installs a tools-only stdio MCP server over the same Gateway session and the trusted `mcp` lease. Discovery projects the installed static Gateway descriptors; resources and prompts are absent, and tools do not invent output schemas. A tool call gets an installation-generated Gateway request ID, never caller-supplied transport, path, credential, or correlation authority. Protocol-shape failures stay JSON-RPC failures; normalized Gateway outcomes are returned as matching text and structured content. Input lines, Gateway responses, complete protocol results, and generic diagnostics are independently bounded. Oversized content is replaced by a typed bounded failure rather than truncated, malformed or invalid frames emit only their protocol class, and diagnostics never reflect input, paths, secrets, or storage errors.

The JSON inspection transport has one exact platform envelope. On Windows, Electron replaces `process.stdin` with an ended stream while leaving inherited file descriptor 0 available, so exact CLI mode pulls bounded chunks from that descriptor without read-ahead. Electron also emits one native CRLF before application JavaScript runs. Windows stdout is therefore exactly that single `\r\n` preamble followed by one nonempty JSON line and its terminating LF; macOS stdout begins with the JSON line and has no preamble. Consumers must match this envelope exactly rather than trim, scan, or filter output. Application JavaScript, raw output descriptors, and Electron's console environment flag cannot retract the native pre-JavaScript bytes, so the JSON contract retains that envelope.

Strict MCP requires byte-zero protocol output. macOS launches Electron directly with exactly one MCP flag. Windows packages a transport-only console SEA relay beside Electron: it accepts exactly that one flag, forwards only an allowlist of OS-location environment variables, ignores Electron's native standard descriptors, and carries request, protocol, and diagnostic bytes over dedicated descriptors 3, 4, and 5. The relay contains no Profile resolver, Gateway, or storage logic. The `afterPack` hook uses the same Node executable to generate and embed the relay payload, then hands the relay to the platform packaging step. This narrowly supersedes the earlier no-wrapper assumption for strict Windows MCP while preserving the JSON envelope and one storage provider.

EOF, a repeated termination signal, input/output failure, and relay pump loss join one drain-first MCP shutdown. They stop input and new Gateway admission; accepted Gateway work drains atomically, then handler and output work drains, and server close is last. The Windows relay ends the child's request descriptor and waits for child/output completion instead of killing accepted work. Only process exit or failure before the protocol pipes exist may use hard termination. A cancellation that wins before Gateway admission prevents authority acquisition; cancellation after admission does not revoke the accepted atomic operation.

The fixed MCP path also governs proof. Environment overrides do not reliably redirect Electron's native `app.getPath('appData')`, and adding a proof-root flag would weaken exact production admission. Local `desktop:smoke` therefore proves the package entry and records persistent MCP as non-authoritative. The required hosted native jobs run under an ephemeral OS user, require the fixed `Eido` root to be absent and on the same filesystem as the already-closed synthetic Profile, then rename that Profile into place before invoking the unmodified production entry. This preserves the database's physical filesystem identity and its durable owner-sidecar binding; a recursive copy manufactures a different identity and correctly opens as `corrupt-or-recovery-required`. The proof removes only the relocated owned root before publishing evidence and never uses a local save.

## Considered Options

- Not chosen: derive the Profile path from package branding or `userData` defaults, because proof, signing, or identity changes could orphan authority and split the singleton key.
- Not chosen: run SQLite in the renderer or Electron main loop, because synchronous transactions and the fixed busy wait would mix persistence authority with UI-sensitive work.
- Not chosen: acknowledge hydration before applying and admitting one exact projection, because lifecycle and acknowledgement-gap edits could be silently lost or falsely conflicted.
- Not chosen: expose direct headless database access or a second storage provider, because local clients must obey the same ownership, query, and shutdown rules as the GUI.
- Not chosen: replace or filter the Windows JSON entry solely to make it begin at byte zero, because its native CRLF is already an exact documented contract. Strict MCP instead uses the narrow transport-only SEA relay above because byte-zero JSON-RPC is an external protocol requirement.
- Not chosen: add an MCP proof-root selector, because the proof must exercise the fixed production path rather than a test-only authority path.

## Consequences

- Packaged Eido and explicit browser development have different persistence adapters; bridge absence in a packaged origin is terminal, not browser-fallback selection.
- Recovery, Portable Export, Duplicate, current-Idea import, GUI commits, bounded inspection, and quit share one installed authority lifecycle. Fresh full-Profile import remains an unbound bootstrap-owner operation rather than an active GUI capability.
- The installed JSON CLI and stdio MCP server use the shared descriptor-backed Gateway session, dispatcher, and their transport-bound existing-only leases without acquiring a second path resolver, SQLite writer, or mutation implementation. The standalone `eido` SEA may instead reach the active GUI owner through ADR 0031's owner-only local IPC endpoint; that live route is globally serialized with renderer persistence and is not exposed through renderer request JSON. No network listener is installed.
- Windows packaging retains the MCP SEA relay and adds the standalone `eido` SEA plus its native local-IPC helper under `resources/bin`; macOS packages the same standalone pair under `Contents/Resources/bin`. Certification records the exact Node version that built the standalone executables. They are entry/transport adapters, not another provider or authority.
- Local package proof and hosted persistent-MCP proof intentionally have different authority: only the ephemeral hosted OS-user boundary can safely exercise the fixed native path.
- Routine renderer saves are intentionally decoupled from the hot interaction path. A three-second quiet window reduces repeated whole-Profile captures during typing and gesture bursts, while explicit checkpoint and lifecycle flushes preserve the existing durable boundary. An unexpected crash can still lose routine changes made within that quiet window, so the window is a responsiveness trade-off, not a guarantee of per-keystroke durability.
