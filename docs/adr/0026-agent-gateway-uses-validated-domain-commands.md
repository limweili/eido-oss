# ADR 0026: Agent Gateway Uses Validated Domain Commands

Status: accepted

## Context

Eido is intended to let local AI agents such as Codex and Claude inspect a user's graph and act on the user's behalf. Direct file or SQL mutation would bypass the one-writer commit funnel, validation, optimistic revision checks, undo/playback semantics, Intent Log attribution, migrations, and recovery. A network service would also unnecessarily broaden the threat model of an offline desktop product.

## Decision

External AI agents use one **Agent Gateway** that exposes versioned, allowlisted, machine-readable inspection and domain-command contracts. A CLI is the universal baseline and a local stdio MCP server is a thin adapter over the same command service; neither implements separate Board logic. The first production transport is local process stdio, not a listening TCP/HTTP port.

The gateway never exposes arbitrary SQL, arbitrary filesystem access, raw Electron IPC, API credentials, or an unrestricted patch primitive. Every mutation names its command/schema version, expected Profile revision, idempotency key, and requested domain action; trusted gateway context injects actor, transport, and client transaction identity. Eido validates the complete batch, applies it atomically through the same mutation and persistence rules as the UI, records agent attribution and meaningful events, and returns structured results and stable error codes. Profile revision is the sole optimistic-concurrency token; transports do not introduce a separate Board revision.

"The same mutation rules as the UI" is a semantic requirement, not permission to copy UI-store policy into a transport. GUI and Agent callers share transport-neutral graph kernels for Card placement, group membership, layer assignment, and Connection admission, orientation, duplicate rejection, and Result routing. External geometry fields also have declared magnitude bounds chosen so downstream placement and layout arithmetic remains finite.

At most one process owns mutable Profile authority. A gateway either routes a request to the active owner or acquires the same exclusive Profile ownership for a headless operation. If it cannot prove ownership or safely route the command, it fails with a machine-readable busy/conflict result; it never edits live SQLite files concurrently. Read operations use a consistent snapshot and follow the same redaction and capability rules.

ADR 0029 installs the shared local routing prerequisite. Electron main owns one fixed-path utility session for the active GUI and trusted `cli`/`mcp` variants of one lazy existing-only headless lease factory. Above that lease, one transport-neutral Gateway session exposes `describe`, `invoke`, and `close`. One installed descriptor registry co-locates names, schemas, versions, bounds, availability, normalized failures, and invocation planners. `describe` projects its static public metadata without opening Profile authority, while `invoke` uses the colocated planner. `agent.capabilities` exposes the Agent-specific surface in enabled, human-only, system-only, and prohibited classes without acquiring authority; raw `profile.capabilities` retains compatibility information for executable historical Mod commands. The first valid authority-requiring invocation single-flights one lease and retains it for the session; close stops admission, drains accepted work, then closes and joins the opened service. Trusted transport is bound once in private utility initialization and cannot be selected by request JSON.

The packaged executable selects one exact `--eido-profile-json` mode, synchronously validates and pins its fixed installation root before yielding, then allows bounded request admission and Electron readiness to complete in either order. Both must complete before lease acquisition; the CLI consumes the persistent session for exactly one caller request, then joins close before stdout. A request may invoke status, raw or Agent-filtered capabilities, canonical bounded record/spatial/result/Mod queries, or one surface-v5 command batch. Surface v5 retains the prior Board behavior and adds active-Idea selection, Ask model selection, shared Card identity, multi-Card arrangement and layering, explicit Group membership, Output version choice and acceptance, and the direct/template Mod lifecycle. These are named domain commands with transition evidence, not a generic Card or record patch.

`idea.create` remains a Profile-scoped aggregate command: one trimmed, bounded display name deterministically creates an inactive Idea and its canonical empty Board, returns both stable identities, and appends one Profile-owned `idea.created` event without changing the user's active Idea. A separate `idea.activate` command makes an existing Idea the sole active head and records the exact previous/next transition without fabricating a Board edit. Duplicate display names are legal because IDs are authoritative. The Board surface creates and domain-edits Note, Ask AI, Title, Group, and Conversation Cards; it deletes those kinds plus the complete Result closure, but cannot directly create/edit generated Result content or write Run-owned transcripts/follow-ups. Card creation provides explicit bounded position or bounded `near` anchors, never both. Anchor resolution and deterministic placement occur inside the expected-revision plan, the receipt returns the chosen position, and a connected thought composes `card.create` plus `connection.create` in the same existing batch. Ask-to-Ask Connection creation follows the same shared graph rule as the canvas: when the upstream Ask has not run, it may create an empty Result Card/Block shell and route Ask → Result → Ask. The shell contains no Output, version, Run, or generated content and does not relax Run-only output authorship.

Fresh success is exact v5. Persisted surface-v1 through surface-v4 receipts are accepted only when `replayed: true` and the submitted request validates against that exact historical surface. Opening, reading, previewing, conflicting, failing audit or transaction, or exactly replaying a retained v3/v4 Profile leaves its ledger constraint unchanged; the first successful v5 apply widens it atomically with the v5 history row. The lease does not seed a missing Profile, choose another path, or open SQLite outside the utility. ADR 0029 also records the exact Windows-native CRLF preamble imposed before Electron application code.

## Considered Options

- Chosen: CLI plus stdio MCP over one validated local command service.
- Not chosen: teach agents the SQLite schema and allow direct writes, because storage layout is not a domain API and cannot preserve Eido's mutation invariants.
- Not chosen: a localhost HTTP API for the first release, because stdio supplies local tool interoperability without an open port, bearer-token lifecycle, origin policy, or orphan-server risk.
- Not chosen: a generic JSON Patch endpoint, because syntactic patches cannot enforce graph relationships, Mod semantics, provenance, or command-level authorization.
- Not chosen: MCP-only access, because a stable CLI/JSON contract remains usable by scripts, tests, release agents, and tools without an MCP host.

## Consequences

- Existing machine-readable action contracts are the inventory and policy input, not automatically a public command surface; commands are admitted deliberately and tested end to end.
- Agent writes can be replayed, diagnosed, rejected on stale revision, and attributed without making agents a second source of truth.
- The gateway must provide dry-run/inspection paths, bounded output, redaction, capability discovery, idempotent retry, conflict handling, and audited command coverage.
- Live routing versus exclusive headless ownership is an implementation detail behind one contract. Both routes use the installed fixed path, the same utility-owned provider, typed ownership outcomes, and joined close; two concurrent mutable authorities are prohibited.
- The shared persistent Gateway session derives discovery and dispatch from one installed descriptor registry. Static Gateway and four-class Agent discovery open no authority; valid stateful calls lazily share one retained existing-only lease; close drains accepted work before releasing it. Bounded neighbor, bounds, Result-closure, and Mod reads return only public logical data from one Profile revision without importing renderer state. Installed JSON, MCP, and ergonomic CLI adapters reuse the same session and advertise only capabilities callable end to end. They add no caller-selected path, provider, raw storage escape, or network listener. Persisted v1/v2/v3/v4 history authorizes exact replay only, never fresh admission or a translated receipt.
- Remote access, accounts, cloud mediation, arbitrary code execution, and unattended privilege escalation require separate decisions.
