# ADR 0025: SQLite Profile Authority, Blobs, and Portable Exports

Status: accepted

Amended 2026-08-05 for #841: a persisted POSIX `st_dev` value is mount-local
evidence, not a durable volume identity. Device-only drift may be rebound only
after copy-first, full Profile validation under the exclusive owner.

## Context

The current pre-Alpha store rewrites one JSON document for ordinary changes and keeps the Mod library in a separate browser setting. Friends Alpha needs transactional recovery, independently addressable durable entities, safe agent-mediated changes, future Mod templates/wires/presets, and an eventual local semantic index without adding a server or making renderer state the database contract. The earlier plan selected versioned JSON metadata plus blobs and deferred SQLite; the tldraw offline production audit and the founder's near-future requirements changed that trade-off before Alpha became the compatibility floor.

## Decision

The Friends Alpha Profile uses **SQLite in WAL mode as its authoritative local record store**, behind the existing Persistence Port and installed by Electron main. One main-owned Profile utility is the sole packaged process that opens that authority. Large immutable payloads live as content-addressed blobs outside the database. The renderer-facing Board snapshot remains a hydration/serialization contract, not the physical database schema, and one validated writer serializes every durable mutation. ADR 0029 fixes the production path, startup ownership, renderer handoff, and joined shutdown around this physical design.

The native blob module derives immutable final files from SHA-256 content identity, but keeps logical asset identity in versioned `logical-asset` records. An internal owner-coordinator command first revalidates the existing reachable closure, then stages and flushes incoming bytes, verifies their digest, and atomically promotes the final file before the SQLite revision can acknowledge its logical reference. Card records retain ordered logical asset IDs; hydration resolves verified bytes back to the path-free `CardAsset.dataUrl` contract. Equal bytes share only the physical file, never logical IDs or provenance. Raw bytes and physical paths stay out of logical records, revision batches, receipts, Intent events, and diagnostics. Removing a logical reference does not delete the final blob: current-revision references are only one root set, so recovery and Portable Export must supply their complete roots before collection can become destructive.

On POSIX, promotion reopens and flushes the final file after rename and flushes created, source, and destination directory entries before SQLite acknowledgement; this follows the [Linux `fsync(2)` durability boundary](https://man7.org/linux/man-pages/man2/fsync.2.html), which requires a separate directory flush for its entry. Public Node/libuv cannot provide the equivalent Windows sudden-power-loss namespace guarantee: Windows uses stage-file `fsync`, atomic rename, read/write reopen `fsync`, rehash, then acknowledgement, while namespace durability remains best effort. Any reachable final missing after reopen is recovery-required rather than silently repaired. Canonical directory identities are checked before and after path operations and all Eido-owned mutations remain inside the owner FIFO. A malicious same-user filesystem adversary is outside #461's guarantee: Node exposes no atomic `openat`/`renameat` seam, so the fences detect and contain ordinary or Eido-owned replacement but do not claim to close that syscall window.

Mutable authority is coordinated through a stable SQLite sidecar derived from the canonical physical Profile path. Its exact connection enters verified `locking_mode=EXCLUSIVE` and proves acquisition transactionally before WAL access, then remains open for the owner-session lifetime. Acquisition rejects path aliases that cannot be canonicalized, replaced or multiply linked authority files, and an existing Profile whose sidecar is missing. It never steals authority using a timeout, heartbeat, PID, or failed route attempt.

The persisted Profile file fence uses device, inode, and nanosecond birth time,
but their lifetimes differ: inode and birth time identify the file within the
mounted filesystem, while `st_dev` identifies the current mount and may change
after a macOS/APFS reboot or remount. When and only when device differs while
inode and birth time still match, the exclusive owner preserves DB/WAL/SHM,
strictly validates the copied Profile's complete revision, logical, and blob
closure against the sidecar's trusted Profile ID and revision high-water, then
compare-and-swaps the stored device number without creating a logical revision.
Any inode, birth-time, link-count, Profile-ID, high-water, revision, logical, or
blob mismatch remains recovery-required. General in-session physical equality
continues to require all three fields.

Each acquisition advances a monotonic sidecar generation and creates a private random token. Both values are bound into physical Profile metadata and checked inside the same transaction as every admitted revision; health reads also fail closed unless the same live capability and Profile fence remain valid. Caller-visible `ownerId` is observational metadata, not a credential. Raw token/generation fields are not accepted as authority: the coordinator issues a runtime-opaque capability bound to the exact live sidecar connection, canonical Profile path, sidecar file identity, and current sidecar row. A maintenance transition may stop admission, drain accepted work, close the Profile handle, and reopen or replace the Profile while retaining that capability and the same sidecar connection. Normal close releases that handle last. The sidecar and its token are device coordination state, not logical records or Portable Export content.

Recovery deepens that same sidecar authority instead of adding another lock. The sidecar binds the logical Profile identity, a revision high-water, and one unfinished restore operation. Every acknowledged ordinary or asset commit raises the high-water after the Profile transaction and before its receipt returns. A corrupt, missing, or physically replaced Profile enters recovery-only mode while the exact sidecar remains held; only inspect, explicit restore, and close remain admitted. A recovery head is healthy only when its candidate, source revision, observed high-water, reserved revision, and operation ID exactly close over promoted or completed sidecar evidence.

Owner-FIFO recovery points use SQLite's backup primitive to publish standalone `profile.sqlite`, strict `manifest.json`, and completion-last `complete.json` generations. Candidate admission verifies the database digest and size, supported versions, integrity, exact revision/receipt/Intent closure, full hydration, and exact reachable blob closure. The newest three verified generations are retained, and their blob roots join live roots for non-destructive collection accounting.

Restore durably reserves `highWater + 1`, quarantines the current database/WAL/SHM, reverifies the selected generation, resets only the exact operation-owned stage database/WAL/SHM, binds copied bytes back to the verified digest, appends explicit recovery metadata, and atomically promotes from a same-directory stage. Reopen, logical/blob verification, new physical-identity binding, and operation completion all occur before admission resumes. Fault retries reuse the same reservation; a completed request replays without mutation only while that recovery revision remains the verified current head. POSIX directory entries are flushed; public Node/libuv still makes Windows namespace sudden-power-loss durability best effort, and Node cannot close a malicious same-user pathname swap between individual syscalls.

Durable records use global stable IDs, explicit per-record and envelope versions, logical revision and causal metadata, and payload validation. The physical design may retain evolving domain payloads as versioned JSON within independently addressable records until query or integrity evidence justifies narrower columns; adopting SQLite does not authorize premature normalization of every Card or Mod field.

Opening an existing recognizable Profile validates all seven persisted version axes through a read-only preflight before any Profile-schema DDL or logical write. A value newer than the implementation supports is a typed `unsupported-future-version` refusal and cannot enter recovery or mutate the Profile head/schema. A new or empty explicitly seeded destination may initialize the current schema. A structurally different future physical format still fails closed, but precise typed classification of such a format belongs to a future format-discovery contract rather than guesses made from today's table layout.

A versioned GUI projection validates only its declared renderer-owned logical view. Native recovery-point summaries remain preserved owner state but are excluded from the current logical projection and validation view; GUI commits cannot replace or erase them. GUI projection version 1 admits only the exact portable `profile-setting-locale` record with canonical `{ locale }` value; additional portable Profile settings require an explicit schema and projection-version extension rather than generic JSON admission.

The native owner persists an accepted GUI projection as its own revision-history class. It is neither a public command batch nor a Duplicate/import lifecycle event: reusing either class would invent false Agent/Intent or transfer semantics in durable history. Durable request evidence is the digest of the complete canonical request plus a canonical path- and byte-free envelope that repeats and binds that digest; the hydrated request itself is not copied into SQLite. The canonical receipt closes over exact changed and deleted record IDs, the appended Intent suffix whose actor must equal Electron main's hydrated `intentActorId`, and consumed ordinary-Idea authorization IDs; native admission preserves the exact submitted Intent prefix, rejects a mismatched appended actor, and never rewrites attribution. A normalized per-revision insert/update/delete ledger keeps that closure independently checkable after later revisions change or remove the same rows; current-head validation additionally equates non-delete evidence to the rows stamped at that revision. Historical tombstones permit an omitted Idea to remove its entire owned closure, including immutable Intent history, without treating that deliberate deletion as corruption. Command, lifecycle, recovery, and GUI evidence are mutually exclusive at a revision; exact GUI replay and cross-ledger idempotency collision detection run before optimistic conflict or authorization admission. The ordinary-create bridge receipt exposes only the correlated Idea ID, authorization success, and the canonical owner-issued creation time; the renderer uses that exact time for the new Idea and Board while the authorization ID and remaining proof stay in main. An unused authorization may be returned again while live or replaced after expiry/staleness, while a consumed authorization remains permanently one-use. Authorization consumption, record diff, receipt, change ledger, and revision advance share one SQLite transaction, while blob promotion happens under the same owner FIFO before row acknowledgement. Unchanged logical records retain their existing creation/update revisions, and the recovery manager observes both a new commit and an exact replay before the native operation resolves. This dedicated seam is an implementation-derived correction to the earlier operational assumption that an existing revision class could be reused.

Native Agent command execution likewise owns a distinct revision and record-transition ledger rather than reusing the legacy internal command writer. Fresh installed command authority is surface v5. It retains prior Board/Connection and Mod commands, then adds sole-command active-Idea selection, Ask model selection, shared Card identity, bounded multi-Card arrangement and layering, explicit Group membership, Output version choice and acceptance, and direct Mod-instance creation/configuration/deletion. These are exact domain commands with bounded transition evidence, not a generic record patch. `idea.create` still inserts one bounded inactive Idea and canonical empty Board with immutable `idea.created` evidence; `idea.activate` changes only the Profile head selector and `lastOpenedAt`, returning and recording the exact previous/next active identities. The Board matrix creates and domain-edits Note, Ask AI, Title, Group, and Conversation Cards; deletion additionally admits Result cleanup, including its complete Output/version/transcript/follow-up closure. Generated Result content and Run-owned transcripts/follow-ups remain unavailable to Agent mutation. Surface-v3-and-later Connection creation follows the shared graph rule for Ask chains: connecting an unrun Ask to another Ask may create the empty Result Card/Block shell plus its two structural Connections. That shell is reversible graph structure, not generated output; only a Run may add Output records, versions, or generated content. Historical surfaces v1 through v4 remain readable only for exact replay under their persisted descriptors and are never translated into v5 meaning or admitted as fresh success. The installed capability/receipt surface is v5 while the command request, schema, Gateway, utility protocol, and physical ledger remain version 1. Native admission binds the trusted actor, transport, Profile, natively minted client transaction identity, commit identity, and commit time. Dry-run plans in a read transaction with owner-minted nonpersisted preview context; apply mints durable context and persists the plan, receipt, semantic events, transition ledger, bindings, records, and head in one write transaction. Deterministic result IDs, Mod nested IDs, and chosen Card positions match between preview and apply, while preview returns no commit or durable event IDs and performs no write. A Card create request supplies exactly one of bounded explicit position or a non-empty bounded set of raw Card IDs/Deep Links; Deep-Link viewport values are ignored, canonical anchors are resolved at the pinned revision, and placement runs inside the same plan as the eventual commit. A connected-thought journey is one existing `card.create` plus `connection.create` batch, not another mutation primitive.

Agent history has four deliberately separate compatibility dimensions: the physical Agent-ledger format remains version 1, each revision persists its installed command-surface version, receipts are decoded as exact v1, v2, v3, v4, or v5 shapes, and the `profile-agent-event` logical record has its own record/payload version 1. Persisted surface selection governs request replay, receipt decoding, event-binding shape, attestation, and recovery; v1/v2/v3/v4 replay remains readable after the store installs v5. The v2 receipt first added exact Profile-event IDs and effects count, and v2-through-v5 bindings discriminate `intent-event` from `profile-agent-event`; historical request, descriptor, receipt, and binding meaning remain exact rather than being reinterpreted by the process default. The v3 Card-create result additionally closes over the chosen `{ x, y }` position, v4 adds the `idea.create` result and event, and v5 adds active-head, organization, Result-selection, and direct-Mod outcomes without advancing either the command envelope or Profile-event record version.

Each surface-v2-through-v5 template create, update, or delete appends exactly one immutable Profile-owned Agent event, including commands whose aggregate record transition later folds to zero. Idea creation and v5 activation likewise append one Profile event closing over their exact aggregate births or head transition. A direct Mod create or template stamp appends no Profile event: it records only real Board Intent and the Card, Block, Mod-instance, and optional Connection transitions it actually creates. Commands folded inside one revision share the commit timestamp, so the internal aggregate planner permits timestamp equality only after that template has already changed in the same aggregate; ordinary cross-revision template updates remain strictly later. Positive Agent-event `seq` values are strictly increasing in Profile-owner ordinal order, but an imported baseline need not start at one. Native reopen treats that retained import as the seed baseline, then requires each later event in receipt `profileAgentEventIds` order to occupy the exact next Profile-event ordinal with `seq` equal to the prior maximum plus one; a monotonic current head is not sufficient derivation evidence. GUI projection preserves Profile Agent events but cannot insert, update, or delete them. Full-Profile Portable Export/import round-trips them, while selected-Idea Duplicate/import excludes the Profile-owned history and preserves the destination Profile's existing events exactly once. The lossless record-oriented legacy Card/asset planner recognizes and preserves these records; its narrow legacy snapshot encoder and hydrator explicitly refuse them rather than silently discarding history.

Fresh seed and full-Profile import persist an ordinal-ordered canonical manifest of `{ recordId, logicalRecordDigest }` in the existing singleton `profile_meta` authority. Writer and reader share the Portable Profile's 64 MiB bound over the exact canonical manifest bytes, so construction cannot commit a manifest that reopen refuses. Reopen reconstructs that manifest only from Profile Agent events whose `createdRevision` and `updatedRevision` both equal the seed revision, requires exact canonical equality, and rejects every later GUI, Agent, or opaque transition targeting an anchored ID before continuing the post-seed ordinal/sequence chain. This is a local consistency root, not a second history ledger or protection against rewriting both the manifest and all covered data; that stronger claim would require an externally authenticated root.

Installed JSON, MCP, and ergonomic CLI adapters share one bounded Agent Gateway and the same owner FIFO. Raw `profile.capabilities` retains all 22 executable surface-v5 commands, while Agent command-batch discovery exposes the 15 bounded Idea, Board/Connection, and research-organization commands; ergonomic Mod verbs adapt to the same raw Mod commands without widening MCP's exact-seven inventory. `agent.capabilities` separately classifies enabled, human-only, system-only, and prohibited actions. Bounded spatial, Result-closure, and Mod reads resolve public logical data from one ownership-fenced revision without a renderer dependency. `command.batch` crosses the private utility `apply-agent-command-batch` operation, which injects trusted transport attribution. Fresh success is exact v5; a supported v1, v2, v3, or v4 receipt is admitted only as exact replay when the submitted request validates against that persisted surface. Exact replay is checked before stale-head conflict. The active GUI owner exposes the same calls only through the authenticated live-routing boundary, never through renderer-supplied SQL, paths, owner credentials, credential material, or transport identity.

Every ordered installed-Agent Intent carries `claimedTransitionEvidence { version: 1, count, sha256 }`, and every command binding repeats its ordered per-event `{ eventId, role, evidence }`. The digest is domain-separated and commits the installed descriptor version, the complete admitted request (including idempotency, expected revision, and `dryRun: false`), trusted Profile/actor/transport/client-transaction/commit/time context, command index and command, exact result, event role, exact semantic planner Intent with owner stamps and the evidence field omitted, and a canonically sorted set of logical transition shapes. Each shape contains record identity/kind, operation, canonical before/after digests, and one causal claim. Inserts belong to their birth event, deletes to their death event, and an aggregate surviving update belongs to its chronologically last actual writer across explicit edits, geometric Group reconciliation, and delete-driven ordinal normalization. Through-Result creation splits Result Card plus Block, source-to-Result Connection, and routed Connection across their three Intent roles. Card deletion owns its exact nested cascade; folded or net-zero commands still receive signed zero-shape evidence. The earliest explicit `card.create` event owns add/change/remove reconciliation of other existing Cards against pre-existing Groups; the created Card remains birth-owned, generated Result Cards never become reconciliation roots, and a later folded deletion may differ from its pre-batch tombstone only by that group-only transition. Ungrouping removes the optional `groupId` field rather than retaining an undefined value in native JSON.

Current-head recovery re-runs the exact planner against the rewound base and verifies the attestation plus transition chain. Historical recovery deliberately does not reconstruct an old graph from later state; it verifies the immutable semantic Intent attestation and the continuous canonical record-digest chain instead. An Agent Intent payload can never be updated after insertion. A later exact deletion is allowed only through that continuous canonical chain; opaque or otherwise unproven mutation fails closed. This rejects coherent rewrites of historical placement/topology, zero-transition targets, request idempotency, and trusted transport even when ordinary row/request/receipt digests are recomputed. Every later GUI record change therefore stores nullable SHA-256 digests of its canonical logical before/after records. Validation chains Agent and later GUI transitions per record, including deletion and reinsertion generations, and checks the surviving head or absence. The 4,194,304-byte durable-change limit is enforced before commit and rechecked from stored byte lengths before reopen parsing or canonical hashing. Pre-upgrade GUI rows are allowed only as legacy barriers before the first Agent anchor; legacy internal command and lifecycle writers are explicit record-specific opaque barriers because they do not retain canonical transition images. We deliberately do not introduce a partial global journal: making one trustworthy would require atomically migrating every historical writer and recovery path, while the bounded Agent-to-later-GUI chain closes the new correctness claim without pretending older evidence exists.

Recovery compatibility is equally narrow. A retained database from before Agent history existed may omit both Agent ledger tables only while it is being inspected as an explicit read-only legacy recovery candidate. Missing exactly one table is corruption, and ordinary inspection remains strict. A pre-v2 Agent ledger may omit both additive surface/Profile-event columns: read-only inspection interprets those two missing columns as surface v1 with no Profile events, while a mutating open transactionally adds both columns and widens the closed logical-record-kind check before validation continues. One missing v2 column, an invalid stored surface, or incoherent event IDs is corruption. A shipped v1/v2 ledger whose surface constraint admits only `{1,2}` is widened on mutable open to the retained v3 constraint by rebuilding the parent Agent event table and its foreign-key child together inside the existing write transaction. Retained v3 and v4 constraints remain unchanged across open, read, dry-run, conflict, failed audit/transaction, and exact historical replay. Only the first successful surface-v5 apply rebuilds either constraint to `{1,2,3,4,5}`, inside the same write transaction immediately before inserting its v5 evidence. Each migration count-checks and bidirectionally compares every copied parent/child column before replacement, then requires `PRAGMA foreign_key_check` to remain empty. This is the deliberate one-way compatibility edge: old evidence is preserved exactly and remains replayable, and an older `{1,2,3,4}` binary remains usable until a v5 history row actually commits. A missing seed-event manifest column is likewise interpreted as canonical empty only when the complete shipped-v1 generation is present: the closed record-kind schema cannot contain `profile-agent-event` and, when Agent tables exist, both v2 columns are absent. Mutable open adds the empty column transactionally, while fresh seed and full import write the actual manifest. Mixed v1/current generations are corruption; whole Agent-table absence remains the separately governed explicit legacy-recovery case. Any observed seed event without its matching anchor fails closed. A verified copied recovery stage installs the complete current schema transactionally before it can become live authority, so retained generations are never mutated in place and a broad `no such table` catch cannot hide malformed evidence.

The GUI persistence queue captures candidates iteratively within explicit depth, node, and escaped UTF-8 byte budgets before they cross the native seam. Deterministic invalid and unsupported-future results terminate that generation and permit newer queued work to proceed; only genuinely unknown transport or commit outcomes retain an exact request for uncertain retry. Conflict reconciliation is bound to its opaque token and generation and cannot discard or supersede a newer captured edit, while saved/flush state requires exact durable-clean revision confirmation.

The Mod library moves into the Profile as first-class versioned template records. Board Mod instances remain frozen, self-contained stamps as required by ADR 0022. Current supported Mod and control fields are validated strictly, while stamping persists immutable stamp-time source template/version and source-to-instance identity-map provenance independently from the instance's subsequently editable current Mod payload. Unknown JSON-safe extension fields remain optional, opaque, inert, and round-trip preserving; storage does not claim active validation or generic reference remapping for future wires, presets, faces, permissions, layout, control kinds, or dangling-reference semantics before those schemas exist. This does not implement the future Mod UI or permit executable Mods.

A **Portable Export** is the stable user transfer and backup boundary. It contains a versioned manifest, complete logical Board/Profile data in an inspectable interoperable representation, referenced blobs, and integrity evidence. Raw SQLite files, WAL sidecars, and recovery working state are implementation details and are not presented as the user's portable backup format.

Portable Export version 1 uses one deterministic classic STORE-only ZIP layout whose local records, central-directory records, single empty-comment end record, and archive end are exactly contiguous; gaps, trailing bytes, duplicate end records, and ZIP64 are refused. Physical observation CRC-checks the bounded manifest and Profile entries. Admission verifies each blob's CRC32 and descriptor SHA-256 during the same once-only bounded stream into operation-owned staging, then exposes only the verified staged handle; validation and import never reread a mutable container entry. Duplicate and current-Idea import rebase identity-derived source-freshness hashes and dismissal signatures from exact verified source asset bytes so fresh, changed, and dismissed meaning survives identity remapping while causal provenance and opaque data remain untouched.

The native owner exposes exactly four queued lifecycle operations: `exportPortable`, `importPortableIntoFreshProfile`, `duplicateIdea`, and `importIdeaClosure`. Full Profile transfer is streamed under the Portable v1 bounds and never constructs a base64-hydrated Profile. Duplicate and current-Idea import instead use a selected-Idea envelope whose v1 preflight admits at most 16 MiB of unique decoded asset bytes and 24 MiB of projected hydrated data-URL code units; legacy Idea/Board sources enforce the same envelope from canonical base64 lengths before decoding or materializing bytes. Exceeding either bound returns the non-retryable `idea-remap-too-large` result before blob opening or mutation. These two operations write an explicit additive lifecycle revision and receipt. They do not forge a public command batch or a semantic Intent event. An exact response-loss retry is probed before optimistic revision rejection; current-Idea import fully reopens and verifies its declared source blobs before replaying a receipt, and every successful lifecycle replay re-observes the committed revision so recovery high-water can be repaired after an interrupted acknowledgement.

A genuinely fresh full import begins with an unbound exclusive owner sidecar. Verified content-addressed blobs publish first. A closed, integrity-checked, same-directory SQLite stage then records the imported logical Profile at its source revision without owner, receipt, recovery, or working-state rows. Only after the sidecar durably owns the operation/key, canonical request digest and integrity root, canonical logical digest, claimed stage path/digest/size, exact blob roots, and base receipt may the coordinator atomically hard-link the absent canonical DB name without overwrite. The same sidecar transaction binds that physical identity and advances the import state before the fenced store opens. Opening legitimately changes SQLite bytes by installing `profile_owner_fence`, so restart proof uses the staged digest only while unbound and uses SQLite integrity plus the exact logical digest, Profile identity/revision, and streaming blob-root evidence after bind. Normal admission stays unavailable until that asynchronous verification, recovery high-water initialization, and durable completion marker finish. Process-local WeakMap handles are capabilities for a live step, never crash evidence.

This ordering never exposes a partially imported logical Profile. An interruption before durable reservation may leave only unreachable content-addressed finals and private DB/blob stages; the next exclusive acquisition removes exact private stage candidates not referenced by a pending sidecar row. Because a reservation commit may become durable before its caller receives acknowledgement, any attempted reservation preserves its stage as recovery evidence until reacquisition re-derives whether the row exists and either resumes or sweeps it. An interruption after DB publication resumes from sidecar evidence, including the hard-link-before-stage-unlink and fenced-reopen-before-completion gaps. Incoming archive or staged-source mismatch is stable invalid input before publication. Missing or changed bytes that are already reachable from published authority are `corrupt-or-recovery-required`. A completed full-import retry at the imported revision must still match the reserved logical digest and roots; after a legitimate later revision it verifies the current Profile identity and current reachable roots before replaying the historical receipt. Full import preserves Profile/global IDs, active Idea, and source revision and refuses an existing destination; restore remains the distinct revision-monotonic #462 quarantine/promotion operation.

The pre-Alpha `eido-v3-ideas.json` format is not a compatibility or migration boundary for the SQLite Alpha implementation. Delivery work starts from native SQLite state or public synthetic seeds and does not inspect, copy, migrate, or preserve private local saves. Forward-migration guarantees begin with formats actually shipped from Friends Alpha onward; unidentified abandoned prototypes retain no compatibility promise.

## Considered Options

- Chosen: SQLite WAL authority, content-addressed blobs, and a separate Portable Export.
- Not chosen: keep whole-profile JSON as the Alpha authority, because overlapping writes, recovery, Mods, agents, and future query/index needs would turn custom file code into a weaker database and force a disruptive post-Alpha migration.
- Not chosen: put large binary assets directly into SQLite, because immutable blob files deduplicate naturally and stay independent from record-transaction churn.
- Not chosen: expose the raw SQLite database as the user document, because safe transfer requires checkpointing, compatibility metadata, blob closure, and verification rather than copying an arbitrary live database file.
- Not chosen: normalize every domain field into relational columns before its query and integrity needs are proven.

## Consequences

- Friends Alpha certification includes WAL/checkpoint/crash behavior, corruption recovery, backup/export, and packaged Apple Silicon macOS plus Windows x64 proof.
- SQLite becomes a production runtime dependency whose supported Electron/Node version, backup behavior, limits, and security settings are part of the release contract.
- Build/CI toolchain support and packaged SQLite runtime support are distinct evidence boundaries. As of 2026-07-20, #658 supports the Node 24/npm 11 lines and uses Volta metadata in `package.json` to select the known-good Node 24.12.0/npm 11.6.2 build pair automatically. Compatible patches remain valid; exact pins advance only after fresh lifecycle and lockfile evidence. Electron's embedded Node/SQLite pair is selected and proven separately by #457/#521 and recorded independently.
- The reusable SQLite primitive owns configuration, synchronous transactions, checkpoints, and integrity checks. Electron 43.2.0 embeds the synchronous Node 24.18 `DatabaseSync` implementation, so the installed Profile service executes it only inside one main-owned utility process; neither the renderer nor Electron's UI-sensitive main loop executes the fixed 1,000 ms busy wait. This placement is not a second persistence authority or configuration path.
- Delivery was staged by honest callable capability rather than by prematurely naming a complete adapter. #459 first provided an unregistered lower-level store, and #594 supplied the complete revision-free logical projection plus native row/blob integration. #465 installs those providers at the fixed product path behind one typed utility proxy and renderer bridge; it does not make the physical schema or ownership capability public. Durable replay receipts remain validated projections bound to their revision row, canonical request evidence, and persisted domain evidence rather than a second authority.
- #460's transport-neutral FIFO mutable-owner coordinator is now installed only inside the Profile utility. Its exclusive sidecar, opaque live-runtime capability, private token/generation fence, physical-file identity checks, and authority-preserving maintenance transition remain private; Electron main chooses the one fixed production path and exposes only logical operations over the typed bridge.
- #461 deepens that coordinator with internal `card.asset.add` / `card.asset.remove` admission and a content-addressed blob store constructed only behind its private FIFO. Blob preparation mints an opaque owner/path-bound batch before SQLite may persist a digest reference; the public Agent Gateway allowlist remains unchanged. Promoted-but-unreferenced finals and crash staging files are non-fatal collection candidates, while a missing or corrupt reachable final fails closed as recovery-required.
- #462 adds owner-held generation creation, recovery-only acquisition, strict inspection, and revision-monotonic restore. #465 routes only inspection/restore while installed authority is recovery-required and requires a higher restored revision plus authoritative hydration before normal admission. Retained generations contribute their blob roots; final deletion remains deferred until all live/export/recovery roots are complete.
- #463's active-owner Portable Export, Duplicate, and current-Idea import operations are installed through the same utility/FIFO and renderer rehydration handoff. Fresh full-Profile import remains available only to an unbound bootstrap owner and is not advertised by the active GUI bridge.
- #524 first installed the exact-six Board command manifest through the existing headless JSON CLI, shared Agent dispatcher, private utility protocol, and owner FIFO. Renderer-consumed service and transport contracts may depend only on the lightweight manifest seam, never the installed planner, dispatcher, or gateway implementation; the manifest itself keeps runtime dependencies absent through type-only imports. MCP remains a later adapter over the same service.
- #525 extends that installed authority to the exact-ten surface v2 and adds durable Profile-owned Mod lifecycle history. Fresh success is v2; exact persisted v1 Board replay remains supported without translation, while fresh v1 and v1 Mod requests fail closed. Surface-specific persisted decoding, additive pre-v2 migration, append-only logical/GUI/Portable closure, and transition attestations keep v1 history readable and make coherent history rewrites fail closed.
- #719/#720 install surface v3 without rewriting either historical surface: the Board matrix gains domain-shaped Title/Group/Conversation creation and edits, complete Result cleanup, exact chosen-position receipts, deterministic `near` placement, bounded spatial reads, four-class discovery, and connected-thought composition through the existing atomic batch. The `{1,2}` SQLite surface constraint is widened through an exact-copy parent/child rebuild; this one-way schema change is isolated to the first mutable v3 open and becomes incompatible with an older reader only when v3 history is written.
- Surface v4 adds Profile-scoped `idea.create` through that same deep command-batch seam and preserves v1/v2/v3 exact replay. The retained v3 ledger is not widened by opening or non-writing work; the first successful v4 apply performs the exact-copy `{1,2,3,4}` rebuild and v4 evidence insertion atomically.
- #457 proof packages never apply an Eido identity/Developer ID signature or notarization. The Windows main executable remains `NotSigned` without stripping valid upstream vendor signatures; after fuse mutation, macOS proof resets the ad-hoc seal required to execute on Apple Silicon and verifies `Signature=adhoc` with no TeamIdentifier. Release signing remains owned by #469/#470.
- Mod templates no longer rely on browser-local settings in packaged mode, while Board instances remain portable and library-independent.
- Browser development, in-memory, and fault-test adapters continue behind the Persistence Port; no renderer consumer may depend on SQL, paths, tables, or SQLite availability.
- Derived indexes, including future vector embeddings, are not authoritative Profile records. ADR 0027 records their deferred boundary.
