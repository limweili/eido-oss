# Execution Layer

The execution layer answers: **how does connected thought run as AI work, and how do the results flow back into the graph?** Ask AI, dependency-aware chains, Group compression, Conversations, variations, and follow-ups all execute through graph-derived plans and durable provenance. The packaged Agent CLI can delegate an Ask or Conversation to that same live engine; it does not introduce a second runner. Governing decisions: ADR 0011, ADR 0013, ADR 0008 (provenance), ADR 0006 (agents as contract consumers), ADR 0030 (Mod prompt shape), ADR 0031 (live Agent routing), and ADR 0036 with ADR 0037 (who runs the tool loop, and the second key that decides it).

Reference inspiration: n8n (steps described as versioned data; contracts readable without executing code; thin runners over declared work). Patterns only — Eido's version is built ground-up.

Eido is free and uses only user-funded providers (ADR 0051). Accounts, billing,
managed AI/search, and product analytics are retired. Local thinking, execution,
and Profile ownership retain the same graph and persistence contracts.

It is deliberately absent from compiled instructions and source fingerprints |

Run kinds today: `ask`, `conversation`, group compression, follow-up, variations, and composed Ask chains. Ask B depends on Ask A when A's Result card feeds B's context; `runChain` always runs the pressed target to create a new version, heals stale upstream asks (ADR 0014, #138), and reports what it reused. The Ask card's Run button is the chain trigger: it previews the run with `chainRunPreview`, asks first when more than the Settings threshold of extra steps would run, and cancel on the pressed card stops the whole chain (`cancelChain`), not just the streaming step. A delegated Agent Run admits a bounded OpenRouter-backed non-Agentic Ask-chain or Conversation plan and may request bounded variations; it is not a generic plan, model, prompt, style, turn, provider, credential, tool-loop, or output submission API. The result-card shape is guaranteed by `src/graph/resultRouting.ts`: wiring an Ask into an Ask routes the connection through the upstream Ask's Result card (created on the spot if missing — same helper the run path uses), and boards with legacy ask→ask connections are repaired the same way at load, so a raw ask→ask feeds connection never exists at runtime.

## Invariants (do not break)

1. **Plan before run.** What will execute is derivable from the graph as data before execution starts. New execution shapes extend the plan vocabulary (new step kind or plan builder) — they do not add bespoke engines.
2. **Inputs through the context layer.** Steps read the graph via context queries/policies (ADR 0012), never private traversal. The policy used is part of what a run means.
3. **Everything provenanced.** Every step produces a `RunRecord` and versioned output; no generated text lands only in a card block (ADR 0008). Frozen prompt provenance stays frozen — follow-ups reuse the stored compiled instruction, not a recompile. A follow-up keeps the run model while the provider is unchanged, but uses the active Idea model after a provider switch so an OpenRouter slug is never sent to a local harness or vice versa. A Conversation version can continue only with its producing provider and resolved model; a change starts a new version instead of rewriting history.
4. **Results re-enter the graph.** A step's output is a graph citizen (output version on a result card), so it is automatically context for the next hop. What is visible on the card is what flows downstream (ADR 0011): the chosen version's answer plus its always-visible follow-up thread, flattened through the shared seam in `src/brain/followUpThread.ts` (PRD #236). Follow-up thread changes are content changes — they trip source-change staleness like any other edit. The loop canvas → context → execution → graph is the product; do not shortcut it.
5. **Plans stay lean.** IDs and policy names, never copied card content — plans must not bloat runs, history, or saves (the intent log already clones RunRecords; keep plans out of that amplification path until compaction lands).
6. **Cancelable and streaming-safe.** Every step must support cancel with partial results preserved as provisional. Result follow-ups additionally register their lifecycle before AI admission; losing their owning Board or exact durable destination revokes follow-up provider authority before any further egress or graph write.
7. **Idea system guidance is an execution envelope, not graph context.** The Settings system prompt is prepended at the selected provider boundary (`aiProvider.ts`/`openRouter.ts` for remote calls and the local harness prompt adapter for CLI calls). It must not be copied into `RunRecord.compiledInstruction`, compiler previews, execution plans, or source-context fingerprints; editing it changes future AI behavior without making existing AI cards read as Source changed.
8. **Delegated execution is live, admitted, observable, and checkpoint-owned.** The CLI never carries credentials or model output. Reserve app/session Run and model-call units before start, bind Agent attribution at the trusted transport seam, return a queued identity, and expose only bounded status/artifact references. The admitted schedule is the executable authority: rederive and compare its provider-facing inputs before each egress, mask only exact executor-owned artifacts, and stop when the user changes Result selection or any other admitted input. Headless execution is prohibited. After possible admission, an uncertain submit outcome is nonretryable; the caller must reconcile rather than create duplicate work. Authority loss or quit stops admission, cancels/drains accepted execution and persistence, then captures the final renderer checkpoint—never checkpoint around an active model writer.
9. **Tool use never touches the compiled instruction, and the executor is decided by the key.** This invariant used to read "Eido never runs the tool loop"; ADR 0036 retired that half after a live capture showed provider-executed page fetch reporting nothing to the caller. What survives is the part that was always load-bearing: an Agentic Run appends nothing to the compiled instruction on any path, so it must not enter the compiler, its golden character-pinned tests, execution plans, or source-context fingerprints. With a Linkup key on OpenRouter, Eido runs the loop at the completion boundary; without one, tools are declared to OpenRouter and executed there; a local harness owns its tools outright and is never handed a prose simulation of one. A page the model read is recorded as an address on the run, never copied into a Card the user did not ask for.
10. **Development Profile review has one execution model.** Its preload-latched sentinel fixes Ask, compressed Group, Conversation, follow-up, speaker-name, and compaction execution to `openai/gpt-5.6-luna`. Resolve that model before token budgeting, cache identity, chain freshness, and frozen provenance, then assert it again immediately before network egress. Ordinary and packaged-proof launches retain normal model selection.
11. **Provider access belongs to the user.** Every new provider request uses user-owned credentials or an installed tool. No Eido account, payment, entitlement, flag, managed credential, or managed fallback participates. Historical managed/Hosted provenance remains parse-compatible without granting execution access.

## Future work (prepared for, not built)

- **Parallel step execution**: independent chain branches can run concurrently; v1 executes the topological order sequentially.
- **First-run approval UX**: the policy and grant states exist, but the active owner-default policy requires no prompt; activating approval needs an app-owned decision surface rather than a CLI-provided grant.
- **Multiplayer/cloud assumptions**: plans and runs carry durable IDs (ADR 0003) so future shared boards can attribute and merge execution history.

## Deliberately not built (reach)

These were considered and ruled out. Do not re-propose them from scratch;
re-propose them against the reason they were ruled out. Two of them have since
been built deliberately, and the notes below say which and why, so the list
stays a record of reasoning rather than a fence around it.

- **A tool-calling loop inside Eido.** Ruled out here, then built (ADR 0036). The ruling-out reasoned that the loop bought nothing the provider did not already give; a live capture disproved that, because provider-executed page fetch reports nothing to the caller, so the loop is what buys a truthful trail. The loop exists only where Eido can execute the tools itself, with a Linkup key on OpenRouter. The harness half of the old reasoning stands untouched: local harnesses own their loops and Eido builds nothing beside them.
- **Pre-flight web research.** Searching before the run and stapling the results onto the instruction reached every provider, but it spent a search the model did not choose, put text the user never wrote into their own instruction, and made "same graph, same instruction" a promise with an asterisk. Retired with ADR 0033, and still retired.
- **A search credential of Eido's own.** Removed with ADR 0034, then restored as an optional second key (ADR 0037), because ADR 0036 gave it what the removed key never had: an execution path the default run calls whenever the key exists. The rule that survived is the test itself: a key the product would only use in a corner stays rejected.
- **MCP.** A server per capability, running alongside the app, whose tool list enters every prompt. For a few operations that is a large amount of context and a second process to supervise. Linkup publishes an MCP server; wiring it into the local harnesses stays documented rather than automated, because those harnesses own their tools (ADR 0033) and a user may add it to their own CLI themselves.
- **Self-hosted search or crawling.** An index is a product, not a feature.
- **A `web` Card kind.** Its context contract would be identical to `note`. A Note that remembers its address buys connections, compaction, staleness, playback, search, and export at no cost.

## How to extend

Adding a new way to run AI? 1) Describe it as a step kind or plan builder in `executionPlan.ts`, 2) get inputs via a context policy, 3) execute through the run engine with full provenance, 4) make results re-enter the graph as versions, 5) update this doc's tables.
