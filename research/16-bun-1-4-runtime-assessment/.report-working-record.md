# Report working record

## Writing brief

- Goal: help Eido's founder decide whether and where Bun 1.4 is worth adopting.
- Reader: founder/product owner with enough technical fluency to judge architecture, but needs payoff before mechanisms.
- Authority: the reader can authorize a canary or migration; implementation remains outside this research task.
- Priorities: protect Profile durability and product behavior first; then developer throughput; avoid false performance precision.
- Constraints: point-in-time sources as of 2026-08-23; no real Profile; no production code migration; percentages are estimates unless marked measured.
- Success: reader can state the recommendation, replacement boundary, category effects, long-term trade-offs, and the evidence that could change the decision.
- Material ambiguity: annual Eido install and waiting cost is unknown and could change whether a package-manager canary is worth its 3–7 day cost and continuing maintenance.

## Step 3 decision

`proceed-with-minor-assumptions`. The product-runtime recommendation needs no material assumption because process ownership is source-grounded. The package-manager recommendation is conditional on a measurable threshold. The missing baseline is visible as the opening judgment condition rather than hidden.

Minor assumptions:

- The founder values Profile safety and release reliability above clean-install speed. Basis: ADR 0025, ADR 0028, ADR 0029, and the repository's certification gates. Validation: reader can reject the priority explicitly.
- Percentage ranges are planning bounds, not commitments. Basis: no Eido-on-Bun benchmark. Validation: the recommended canary measures them.

## Context dossier

- Purpose: decide whether Bun 1.4 is worth implementing in Eido.
- Current reality: Eido pins Node 24/npm 11 and ships Electron 43 with Chromium, Vite, React, Playwright and Node SQLite authority.
- Why now: Bun 1.4 released 2026-08-20 with a Rust rewrite and new compatibility claims.
- Stakes: a toolchain experiment is reversible; a Profile or release-runtime migration can cause broken builds, lost work, or recovery divergence discovered by developers or users late.
- Criticality: Profile one-owner/durability/recovery invariants and signed packaged certification are non-negotiable.
- Constraints: macOS and Windows release matrix, Electron ABI, Node-first upstream support, no real Profile proof.
- Related work: persistence and execution foundations, ADRs 0025, 0028, 0029, 0031–0039, existing performance gates.
- External context: Bun 1.4 first-party release/docs; Electron/Vite/Vitest/Playwright/Node primary contracts.
- Unknowns: install share of CI, dependency lifecycle compatibility, Bun Vite/Vitest/Playwright packaging behavior, Eido SQLite semantics under Bun.

## Report mode and action

- Mode: `decision-brief`.
- Competing purpose: system lesson, because the report must teach runtime ownership.
- Action requested: choose “do not migrate broadly”; authorize a reproducible shadow installer canary only if measured annual install/onboarding/CI waiting value exceeds experiment and maintenance cost.
- Decision owner: Eido founder.
- Reversibility: high for an uncommitted shadow canary; low for Profile/runtime authority changes.

## Quantitative contract

- Measure: estimated percentage change in wall-clock time relative to current Eido path. Negative product effects are described in words rather than encoded as fake precision.
- Unit: percent faster or slower, always labelled.
- Population/sample: Eido workload category, based on source ownership and first-party upstream benchmarks; no Eido Bun sample exists.
- Denominator: current Eido category wall time.
- Timeframe: toolchain and docs inspected 2026-08-22 to 2026-08-23.
- Missingness: show “unknown” where no defensible range exists.
- Transformations: vendor benchmark ratios narrowed using Eido path ownership; these are estimates, not measurements.
- Uncertainty: low/medium/high confidence shown in the audit table; no statistical interval claim.
- Invariants: each range lower bound is not above upper bound; safe-scope product runtime effects stay at zero; install ratio and percentage reduction remain mathematically consistent.

## Adversarial review disposition

- Reproducibility: resolved by preserving exact Bun, migrated lock, registry/trust settings, dependency-tree hash, and lifecycle outputs on an isolated branch or as durable CI artifacts while keeping npm authoritative.
- Script-runner guard: resolved by limiting Bun execution to new unguarded probes unless toolchain policy is deliberately changed.
- SQLite equivalence: resolved by splitting `node:sqlite`, `bun:sqlite`, and `Bun.SQL` into distinct candidates.
- ROI: resolved by replacing the fixed CI-share threshold with annual waiting value versus experiment and maintenance cost, including npm tuning as control.
- Signing: resolved by deferring signing/notarization until outputs differ or a Bun binary is proposed.
- Unsupported ranges: unmeasured cold dev, HMR regression, release, packaged startup, memory, artifact size, and sidecar effects are now unknown rather than precise.
- Vite seams and Node versions: resolved by naming all three custom plugins and separating host Node 24.12.0, Electron Node 24.18.0, and Bun's Node 26.3.0 compatibility target.
- Sidecar alternative: retained as an independent benchmark track, not coupled to installer ROI and not allowed to own Profile data.
