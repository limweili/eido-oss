# Eido runtime fit for Bun 1.4

## Scope and method

I traced the renderer, Electron main, profile utility, AI, CLI, and SQLite seams using the codebase graph first, then checked the corresponding source. I read `docs/foundations/canvas-layer.md`, `context-layer.md`, `execution-layer.md`, and `persistence-layer.md`, plus ADRs 0010, 0011, 0019, 0020, 0023-0026, 0028-0029, and 0031-0039. No real Profile was opened or tested. Percentages below are mechanism-based estimates, not Eido-on-Bun measurements; they are intended to bound likely wall-clock effects, not promise product-latency improvements.

## Causal conclusions

**Fact.** Electron has one main process and separate Chromium renderer processes; renderer code is web code, while Node/Electron APIs belong to main/preload/utility boundaries. See the [Electron process model](https://www.electronjs.org/docs/latest/tutorial/process-model). Eido follows that split: React/React Flow/canvas and default AI fetches are renderer-owned; Profile authority is Electron utility plus synchronous Node SQLite.

**Fact.** Bun's documented strengths—standalone executables (`bun --compile`), Web APIs, and child-process APIs—can help a standalone CLI or a user-selected external harness. See [Bun executables](https://bun.sh/docs/bundler/executables), [Bun Web APIs](https://bun.sh/docs/runtime/web-apis), and [Bun child processes](https://bun.sh/docs/runtime/child-process). An exact Bun 1.4.0 probe also confirms the basic `node:sqlite` `DatabaseSync` path; Eido's stronger durability and ownership contract is still unproved. These are sidecar opportunities, not reasons to move the board or Profile authority.

**Inference.** The most important Eido latency categories—board frames, pointer gestures, first token, model generation, network round trips, and SQLite commit durability—are controlled by Chromium/React/canvas, provider/network/model, and SQLite/utility ownership respectively. Bun can affect orchestration startup and build mechanics, but not those dominant resources. For long AI runs, shortening JavaScript startup is negligible beside repeated provider turns.

**Failure cases.** A broad “replace Node with Bun” change can fail at Eido-specific SQLite durability/recovery/ownership semantics even though the basic `node:sqlite` API works, as well as at Electron `utilityProcess`/`BrowserWindow` APIs, native packaging and signing, CommonJS/ESM export differences, shell/path handling for configured harnesses, stream buffering, and abort/child-tree signal races. Bypassing the utility to write a Profile would violate the ownership and recovery invariants even if a benchmark looked faster.

**Recommendation.** Retain Electron/Chromium/Node SQLite for the shipped app. If adoption is desired, stage it as an independently packaged Bun CLI parser or opt-in harness executable, with disposable-profile and stream/cancellation contract tests. Do not claim a user-facing win until Chromium frame traces, first-token traces, commit receipts, and packaged recovery evidence show one; current source evidence supports build/sidecar experimentation only.

## Uncertainty

No Eido-on-Bun benchmark was run. The exact Bun 1.4.0 probe covers only basic `DatabaseSync` create/insert/select; Eido's WAL/full-synchronous settings, foreign keys, busy handling, CAS, recovery, utility-process ownership, and packaged behavior remain unverified. Bun's compatibility page is a living matrix; its `node:http` streaming note should be rechecked at the pinned version. The ranges above are deliberately conservative mechanism estimates. The high-impact unresolved gap is a disposable benchmark comparing a Bun CLI/harness sidecar against the current Electron/Node process, including streamed deltas, cancellation, and packaged signing—not a real Profile.
