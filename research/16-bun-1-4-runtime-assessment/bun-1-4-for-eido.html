Architecture decision

Keep Bun outside Eido's shipped runtime; measure it at the edge.

Bun 1.4 can cut dependency-install time, but it does not own Eido's board frames, model latency, or durable Profile writes. Adopt nothing broadly until one reversible canary proves annual value greater than its maintenance cost.

Decision rule

Keep Node/npm if measured annual install waiting is cheaper than a canary and ongoing dual-toolchain upkeep. If it is more expensive, test only the installer first. A separate Bun CLI or harness sidecar needs its own workload and ROI.

Technology boundary

Bun replaces tools at the edge, not Eido's product technologies.

04

Lifetime maintenance

One faster installer can create a second runtime to understand forever.

Bun is attractive when a project is Bun-native. Eido will still ship Chromium/V8/Node inside Electron, so broad adoption adds a JavaScriptCore support surface instead of removing the old one.

What gets easier

Fast outer-loop work

  • Install: global cache and fast filesystem backends can cut clean-install waits.
  • Small tools: short process startup and standalone helpers can use fewer resources.
  • Supply chain: dependency lifecycle scripts are blocked unless deliberately trusted.
  • Tool discovery: one distribution includes installer, runner, tests, bundler, server, SQL and executable compiler.

Best case: Bun remains a narrow, measured tool with a cheap removal path.

What gets harder

Two runtime contracts

  • Engines: JavaScriptCore/Bun joins Chromium/V8/Node, with different profiles, serialization, mocks and stack traces.
  • Provenance: npm lock, Bun lock, caches, trust lists, registries and package trees can drift.
  • Support: Electron, Vite, Vitest and Playwright name Node in their primary contracts; Bun 1.x has no equivalent published LTS window.
  • Release: shipped Bun helpers add licenses, artifacts, signing, updates and incident-response work without removing Electron obligations.

Failure timing: contributors discover drift in CI; users discover runtime or storage mistakes after packaging, when correction costs more.

Lifetime rule

Keep one release authority. If Bun becomes a second way to build the product, its maintenance cost can outlive the install time it saved.

05

Conditional action

Measure annual cost first; canary only the seam that can repay itself.

The founder does not need to approve a migration. The decision is whether current waiting cost earns a reproducible experiment.

  1. Build the denominator.

    Measure minutes per cold and warm install, annual install count, CI frequency, onboarding events and waiting-time value. Benchmark npm cache and workflow tuning as the control.

  2. Make the comparison reproducible.

    Persist Bun 1.4.0, migrated lock, registry and trust configuration, dependency-tree hash and lifecycle outputs on an isolated branch or as durable CI artifacts.

  3. Prove equivalence before speed.

    Compare Vite browser and four Electron bundles, Vitest, Playwright health, audit results and unpacked Electron smoke. Sign only if output differs or a Bun binary is proposed.

  4. Keep the reversal cheap.

    Adopt only installer scope if savings repay upkeep. Keep Node/npm as release authority and keep Bun away from Electron and Profile ownership.

06

Evidence audit

Architecture evidence is strong; Eido-on-Bun timing evidence is still absent.

The decision survives because the product-runtime ownership is known. The package-manager conclusion remains conditional because no Eido install or full CI comparison has run.

Largest uncertainty

Annual install and waiting cost is unknown. It can reverse the installer-canary choice, but it cannot make Bun appear inside the current board, provider or Profile paths.

What would change the main recommendation

Only a future architecture that deliberately replaces Electron runtime ownership, or authoritative paired evidence showing a Bun process preserves every Profile and packaging invariant while buying material product value.

Final answer

Bun 1.4 is not worth implementing as Eido's app runtime. It may be worth a reproducible installer canary or one non-authoritative sidecar benchmark, but only after the current cost gives the experiment a positive ROI.
