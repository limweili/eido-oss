# Bun 1.4 runtime assessment

**Research date:** 2026-08-22 (Australia/Sydney). **Scope:** first-party Bun 1.4 release notes and documentation, Bun’s official GitHub CI action/test documentation, and the official Node, Electron, Vite, and Playwright contracts where they define compatibility. Claims below are tagged **Fact**, **Inference**, or **Recommendation**. “Bun.js 1.4” is not the wording used by the inspected first-party release: the canonical names are **Bun 1.4** and **Bun v1.4.0**. Calling it Bun.js is shorthand, not a verified product label ([release notes, 2026-08-20](https://bun.com/blog/bun-v1.4); [homepage, accessed 2026-08-22](https://bun.com/)).

## Release facts

**Fact.** Bun 1.4 was published 2026-08-20 and is the first Rust implementation; Bun 1.3.14 was the last Zig release. The rewrite covered the runtime, Node-compatible APIs, package manager, bundler, and test runner. Bun reports 1,517 additional Node.js tests, targeting Node v26.3.0, plus more than 2,900 fixed issues. The release announcement reports materially lower idle CPU/memory and faster startup, but those are Bun’s benchmarks, not a compatibility contract ([release notes, 2026-08-20](https://bun.com/blog/bun-v1.4); [Rust rewrite, 2026-07-08](https://bun.com/blog/bun-in-rust)).

**Fact.** The release added `Bun.Image`, `Bun.WebView`, `Bun.markdown`, `Bun.cron()`, and `Bun.Terminal`; built-in JSON5/JSONL/JSONC/XML/TOML/archive helpers and Web Streams compression; HTTP/3 in `Bun.serve` (experimental); and Rust-backed `bun:ffi` (up to 3x faster according to the release). It also added `bun run --parallel`, `bun test --parallel`, `bun audit fix`, `bun dedupe`, `bun prune`, and package-license reporting ([release notes, 2026-08-20](https://bun.com/blog/bun-v1.4)).

## Capability and caveat map

| Area | What Bun officially provides | Qualification that matters |
|---|---|---|
| Package manager / scripts | `bun install` is npm-compatible, with `bun.lock`, npm/Yarn/pnpm lockfile migration, workspaces, workspace protocols, catalogs, filters, overrides, patches, isolated or hoisted linking, frozen installs, and platform dependencies. Arbitrary dependency lifecycle scripts are denied unless explicitly trusted. `bun run` executes package scripts; 1.4 adds parallel/sequential script orchestration and glob/workspace filters ([install](https://bun.com/docs/pm/cli/install), [workspaces](https://bun.com/docs/pm/workspaces), [lockfile](https://bun.com/docs/pm/lockfile), [lifecycle](https://bun.com/docs/pm/lifecycle), all accessed 2026-08-22). | **Fact:** this is a practical npm/pnpm replacement. **Failure case:** packages depending on install-time code/native downloads can fail until `trustedDependencies` is deliberately configured; this is a security boundary, not an npm-compatible default. |
| Runtime / TS / JSX | The runtime executes JavaScript, TypeScript, and JSX directly; `bun run`, `bun <file>`, watch/hot mode, Node resolution and broad `node:*` APIs are built in. `Bun.build`/`bun build` handles TS/JSX/CSS/HTML, browser/Bun/Node targets, watch, HMR-oriented HTML development, and single-file compilation ([homepage](https://bun.com/); [bundler](https://bun.com/docs/bundler); [HTML](https://bun.com/docs/bundler/html-static)). | **Fact:** the bundler is not `tsc`: it does not type-check or generate declarations. `bun --hot` is server-side reload, not browser Vite HMR, and re-transpiles all code; Vite `import.meta.hot` support is documented as planned ([watch mode](https://bun.com/docs/runtime/watch-mode)). 1.4 also changes `react-jsx` emission, CSS runtime imports, `.xml` imports, class-field semantics, and several strict Node/Fetch/TLS/WebSocket behaviors ([breaking changes](https://bun.com/blog/bun-v1.4)). |
| Test runner | `bun:test` is a built-in Jest-like runner with TS/JSX, snapshots, mocks, DOM adapters, coverage, JUnit, watch mode, retries/repeats, changed-file selection, sharding, and (new) parallel worker processes. `node:test`’s programmatic `run()` and test stream gained implementation in 1.4 ([test docs](https://bun.com/docs/test); [release notes](https://bun.com/blog/bun-v1.4)). | **Fact:** Bun says it aims for Jest compatibility, not that every Jest/Vitest feature works; `jsdom` is not supported because of V8 APIs (use `happy-dom`). The current Node compatibility table still marks `node:test` partial: many CLI options throw `ERR_NOT_IMPLEMENTED`, concurrency is serial, and reporters, snapshots, module mocking, coverage, watch, and several filters are missing. Prefer `bun:test` for Bun-native suites ([Jest migration](https://bun.com/guides/test/migrate-from-jest); [Node compatibility](https://bun.com/docs/runtime/nodejs-compat), accessed 2026-08-22). |
| Node modules / native addons | Bun implements Node-API from scratch; `.node` modules can be loaded with `require`/`import` and `process.dlopen`, and 1.4 aligns N-API status codes with Node 26. Bun’s docs say most existing Node-API extensions work ([Node-API](https://bun.com/docs/runtime/node-api), accessed 2026-08-22). | **Fact:** this does not mean V8 ABI compatibility. `bun:ffi` is explicitly experimental and has known limitations; use Node-API for stability ([FFI](https://bun.com/docs/runtime/ffi)). The bundler treats `.node` as an asset/file loader, not a magically bundled executable addon ([loaders](https://bun.com/docs/bundler/loaders)). **Inference:** Electron native modules must still be rebuilt against Electron’s Chromium/Node ABI; Bun cannot replace `@electron/rebuild` or make `process.dlopen` thread-safe ([Electron native modules](https://www.electronjs.org/docs/latest/tutorial/using-native-node-modules/); [Electron workers](https://www.electronjs.org/docs/latest/tutorial/multithreading)). |
| SQL / SQLite | `bun:sqlite` remains synchronous, better-sqlite3-like SQLite; `Bun.SQL` offers a promise API for PostgreSQL, MySQL, and SQLite with pooling, transactions, and prepared statements ([SQLite](https://bun.com/reference/bun/sqlite); [SQL](https://bun.com/docs/runtime/sql)). Release notes claim `node:sqlite` passes all 18 Node v26 test files (319 subtests, four Linux skips), backed by the same SQLite implementation ([release notes](https://bun.com/blog/bun-v1.4)). | **Measured evidence (coordinator probe, 2026-08-22):** the official Bun v1.4.0 macOS arm64 binary, downloaded to a temporary directory, was invoked with this command shape: `bun -e 'import { DatabaseSync } from "node:sqlite"; const db = new DatabaseSync(":memory:"); db.exec("CREATE TABLE t (n INTEGER); INSERT INTO t VALUES (42)"); console.log(db.prepare("SELECT n FROM t").get().n)'`. It exited successfully and printed `42`, confirming basic `node:sqlite` presence and `DatabaseSync` execution in that build. The generated reference still says “Not implemented in Bun; consider `bun:sqlite`” ([reference](https://bun.com/reference/node/sqlite), accessed 2026-08-22); it is therefore stale for basic API presence. **Remaining uncertainty:** this probe does not establish all Node v26 test parity or Eido-specific semantics (error behavior, transactions, extension loading, blocking behavior, or platform SQLite differences). |
| HTTP / WebSocket / workers / subprocess | `Bun.serve` provides HTTP routing, WebSockets/pub-sub, streaming, and experimental HTTP/3/QUIC; 1.4 tightens request/header/upgrade validation and adds server-side STARTTLS, shared cluster sockets, and HTTP keep-alive/pipelining improvements. `Worker`/`worker_threads` gained resource limits/stdout/stderr/eval-related APIs, messaging/introspection, and captured stdio. Bun.spawn supports child processes, streams, cgroups (Linux), and the new PTY API ([server](https://bun.com/docs/runtime/http/server); [release notes](https://bun.com/blog/bun-v1.4)). | Bun’s compatibility table still qualifies `node:http`, `https`, `async_hooks`, `child_process`, `cluster`, `tls`, `worker_threads`, and `inspector`: e.g. HTTP server is not `net.Server`, HTTPS sockets are not `TLSSocket`, async hooks are stubs/IDs are zero, child IPC/stdio edge cases differ, and Worker `resourceLimits`/some locks APIs are missing ([Node compatibility](https://bun.com/docs/runtime/nodejs-compat)). HTTP/3 is experimental and requires TLS; do not infer Node QUIC production parity. |
| Standalone / CI | `bun build --compile` creates a self-contained executable, with cross-targets, embedded assets, bytecode options, and `Bun.isStandaloneExecutable`; it is Bun’s alternative to Node SEA ([executables](https://bun.com/docs/bundler/executables); [release notes](https://bun.com/blog/bun-v1.4)). CI can install exact lockfiles via `bun install --frozen-lockfile`; `oven-sh/setup-bun` provides an official GitHub Action, and `bun test` emits GitHub annotations/JUnit ([setup-bun](https://github.com/oven-sh/setup-bun); [test CI docs](https://github.com/oven-sh/bun/blob/main/docs/test/index.mdx)). | The compatibility table marks `node:sea` not implemented; compilation has restrictions (single entry point, output/splitting/public-path constraints). `.node` native addons still need platform/ABI handling. |

## Ecosystem contracts and implications

**Fact.** Bun’s 1.4 release says Playwright runs under Bun, including `playwright test`, UI mode, and `connectOverCDP`; it also says Vitest runs, including coverage and worker pools ([release notes](https://bun.com/blog/bun-v1.4)). Playwright’s own current documentation still describes Playwright Test as running in Node.js and lists Node.js 22.x/24.x/26.x as system requirements ([intro](https://playwright.dev/docs/intro); [running tests](https://playwright.dev/docs/running-tests), accessed 2026-08-22). **Inference/Recommendation:** Bun support is a Bun interoperability claim, not necessarily Playwright’s support contract. Pin and exercise the exact Playwright/browser version; use Node when vendor-supported CI is a requirement.

**Fact.** Vite’s official guide permits `bun install`/`bunx vite`, while its current compatibility note still requires Node 20.19+ or 22.12+; Bun documents `bunx --bun vite` as the explicit way to run the CLI under Bun ([Vite guide](https://vite.dev/guide/), accessed 2026-08-22; [Bun Vite guide](https://bun.com/guides/ecosystem/vite), accessed 2026-08-22). Vite recognizes `bun.lock` for dependency pre-bundling cache invalidation, but Bun auto-loads `.env` before scripts, which can conflict with Vite dotenv expansion ([Vite env](https://vite.dev/guide/env-and-mode); [Vite dep pre-bundling](https://vite.dev/guide/dep-pre-bundling.html)). **Recommendation:** distinguish “Bun as package manager” from “Vite dev/build under Bun”; validate env loading and plugin/native dependencies.

**Inference.** Electron embeds its own Chromium and Node, and native modules must target Electron’s ABI. Therefore Bun is a useful installer/build/test/auxiliary server, but should not be assumed to run Electron itself or to make Electron addons portable. Keep Electron’s runtime and rebuild workflow authoritative.

## Mechanism, uncertainties, failure modes

**Fact:** the 1.4 mechanism is a wholesale Zig-to-Rust rewrite with extensive cross-platform tests, not a thin compatibility shim ([Rust rewrite](https://bun.com/blog/bun-in-rust)). **Uncertainty:** release-note pass rates (for example `node:http`/`fs` around 97%, `node:http2` 93.2%, `process` 84.2%) are snapshots against Node v26 tests, while the living compatibility page changes independently and labels whole APIs “implemented” despite caveats. The `node:sqlite` probe confirms basic presence, but not full parity; generated references can lag, as that page demonstrates. **Failure cases:** trust-gated install scripts, V8-specific packages (`jsdom`, inspector/profiling/V8 serialization), Electron ABI/native modules, Node-only test CLI features, Vite env/HMR assumptions, unsupported Node API options, and experimental HTTP/3/FFI/WebView behavior. **Recommendation:** adopt Bun 1.4 as a high-coverage runtime/toolchain after a project-specific matrix (install with frozen lockfile, native addons, test runner, Vite plugins, Playwright browsers, Electron packaging, standalone binary); preserve Node/Electron where the upstream contract or ABI requires it.
