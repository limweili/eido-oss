# 11 — n8n

> Studied from source: `research/repos/n8n` (shallow clone, `master`, June 2026). Read-only.
> **Role for Eido:** the reference for the **execution graph view** — turning a directed graph of nodes into a *run*. This is the donor for Eido's "playback / automations / simulations" (your validator chain, persona panel, debate-loop). n8n is the most mature open-source example of "a visual node graph that actually executes."

---

## 1. Why n8n matters to Eido

tldraw gives Eido the *graph as a reactive database*; n8n gives Eido the *graph as an executable program*. Your sketch's `NOTE → … → OUTPUT` path, and your automation ideas (series validators, parallel personas, the auto-debate bounce), are all **graph-execution topologies** — exactly what n8n's engine does. The lesson isn't to copy n8n's integrations; it's to copy its **execution semantics**: how a directed graph with branches, merges, and loops is run to completion, with data flowing along edges.

Two confirmations up front:
- **n8n's editor canvas runs on Vue Flow** (`@vue-flow`, the Vue sibling of React Flow) — independent validation of the Flow-family for a *runnable* node canvas ([03](03-reference-projects.md)).
- n8n's execution is **imperative/push-based** (snapshot the workflow, run it), which is the natural counterpart to tldraw's **reactive/pull** store — and reconciling those two is the central synthesis question (§7).

## 3. The data model

### Nodes (`interfaces.ts` → `INode`)
```ts
interface INode {
  id: string
  name: string                 // ← connections reference nodes BY NAME
  type: string; typeVersion: number   // points into the node-type registry
  position: [number, number]   // canvas coords (the node is also a visual)
  parameters: INodeParameters  // the node's config (can contain ={{expressions}})
  credentials?: INodeCredentials
  // execution-control flags — all relevant to Eido's long-running LLM nodes:
  disabled?, retryOnFail?, maxTries?, waitBetweenTries?,
  executeOnce?, onError?, continueOnFail?, alwaysOutputData?
}
```
Note the node carries both **position** (it's a canvas object) and **parameters + execution policy** (it's a program step). One object, two roles — the same fusion Eido wants.

### Connections (`interfaces.ts` → `IConnections`) — source-indexed
```ts
IConnections = { [sourceNodeName]: {
    [connectionType: "main" | "ai_tool" | ...]:
        Array< IConnection[] >          // outer index = OUTPUT index (branching)
} }
IConnection = { node: string /*target*/, type: NodeConnectionType, index: number /*target input*/ }
```
Three things to internalize:
1. **Connections are stored indexed by *source* node.** Finding *children* is direct; finding *parents* requires inverting the map (`mapConnectionsByDestination()`, per n8n's own AGENTS.md). Eido's adjacency index needs to serve *both* directions (tldraw's `bindingsIndex` indexes both `fromId` and `toId` — [09](09-tldraw.md) — which is the better choice).
2. **Typed connections** (`type`: `"main"`, `"ai_tool"`, …) — a single graph carries *multiple edge semantics*. This is a precedent for Eido's typed edges (support / modifier / negative).
3. **Output index + input index** → native support for branching (multiple outputs) and multi-input nodes (merge).

### Data items (`INodeExecutionData[][]`)
Data flowing along an edge is **an array of outputs, each an array of items**: `data[outputIndex][itemIndex]`. n8n is fundamentally **item-stream-based** — a node maps over items. For Eido this is the model for **fan-out generation**: one thought → N variant items flowing downstream (your "drag-to-autofill / branch a thought").

### Graph traversal utilities (`packages/workflow/src/common/`)
Reusable, off-the-shelf graph ops: `get-child-nodes`, `get-parent-nodes`, `get-connected-nodes`, `map-connections-by-destination`. Confirms that even an "automation" tool needs a small graph-traversal library at its core — which is exactly what Eido's context compiler is ([05](05-ai-context-engine.md), [12](12-neo4j.md)).

## 4. The execution engine (`workflow-execute.ts`) — the spine traced

n8n runs a graph with a **data-driven stack machine**, not a naive topological sort. The mechanics (from `run()` → `processRunExecutionData()` and the `addNodeToBeExecuted` / `waitingExecution` helpers):

1. **Seed.** `run()` builds a `nodeExecutionStack: IExecuteData[]`, pushing the start node with an initial empty item (`{ json: {} }`). `IExecuteData = { node, data, source }`.
2. **Main loop** (`processRunExecutionData`): pop the next `IExecuteData`, **execute that node** over its input items, producing `INodeExecutionData[][]` (output-indexed).
3. **Propagate.** For each output connection of the node, take the output items and hand them to each downstream node:
   - If the downstream node's inputs are all ready → push it onto the stack.
   - If it needs inputs from *multiple* upstream branches (a **merge / fan-in**) → park its partial inputs in **`waitingExecution`** (and `waitingExecutionSource`) until every required input has arrived; `addNodeToBeExecuted` decides readiness.
4. **Branch (fan-out)** is free: a node with multiple output connections simply enqueues several downstream nodes.
5. **Loops** are handled by edges that re-enqueue an already-run node; termination relies on guards (`executeOnce`, loop nodes, data emptiness) — i.e. **the developer/graph defines the stop condition**, echoing your insight that "the stop condition is something only the user knows."
6. **Execution order** is explicit and versioned (`executionOrder: 'v1'` vs legacy) — they had to *design* run order, it isn't just left to chance.
7. **Resilience & async**: per-node `retryOnFail`/`maxTries`/`continueOnFail`/`onError`, plus a **resume token** mechanism for pausing/resuming (waits, human-in-the-loop). Directly relevant to Eido's long-running LLM calls and "pause for my input" steps.
8. **Partial execution / "run from here"**: `run()` accepts a `destinationNode` + `runNodeFilter` and can reuse prior `runData`, so you can re-run from a single node without recomputing the whole graph. Eido wants exactly this: "play this thought-path from this focus node."

### How a node references upstream results — expressions (`workflow-data-proxy.ts`)
Node parameters can contain `={{ $node["Marketing Mark"].json.idea }}` style expressions. At run time a **data proxy** resolves these against the run data of named upstream nodes. This is n8n's "how does step B see step A's output" answer. For Eido, the analogue is: a node's prompt template references its **compiled context** (from upstream + weighted connections), with the context compiler ([05](05-ai-context-engine.md)) playing the role of the data proxy.

## 5. Mapping n8n → Eido's playback (your concrete examples)

| Your idea | n8n mechanism that implements it |
|-----------|----------------------------------|
| **Series validator** (novel → feasible → impactful) | Linear chain; engine runs in order; each node's input = previous node's output items |
| **Parallel personas** (Mark / Parker / Bob / Frank / Larry) | One source node with **fan-out** to N nodes; optional **merge** node collects all via `waitingExecution` |
| **Auto-debate bounce loop** | A **cyclic** connection re-enqueuing two thought nodes; stop condition = max iterations / a judge node |
| **Drag-to-autofill / branch a thought** | The **item-stream** model — one node emits N variant items downstream |
| **Reusable MOD component** | A node whose `type` points to a saved sub-graph (n8n sub-workflows; ComfyUI subgraphs — [03](03-reference-projects.md)) |
| **Pause for my judgment** | The **resume-token** wait/resume mechanism |

The headline: **Eido does not need to invent an execution engine.** The stack + `waitingExecution` + item-stream + data-proxy pattern covers series, parallel, merge, loop, and partial runs. Eido's job is to make each node's "execution" = *compile context from the weighted graph, then call an LLM*, and to render the run *live on the canvas* (n8n's editor already overlays per-node run status — the UX reference for "watching a thought play back").

## 6. What to extract for Eido

1. **Separate "the graph" from "a run."** n8n keeps `Workflow` (definition) distinct from `runExecutionData` (a specific execution's state/results). Eido should likewise treat playback as producing a *run record* over a snapshot, not mutating the canvas mid-run.
2. **Stack machine + `waitingExecution`** for series/parallel/merge/loop — proven, simpler than a generic scheduler.
3. **Item-stream data model** (`data[output][item]`) for fan-out variant generation.
4. **Expression/data-proxy** as the mechanism for a node to reference upstream outputs — Eido swaps in the context compiler here.
5. **Per-node execution policy** (retry, continueOnFail, executeOnce) and **resume tokens** — essential for flaky/long LLM calls and human-in-the-loop pauses.
6. **Partial execution** ("run from this node") and **explicit, versioned execution order**.
7. **Index adjacency in both directions** (n8n's source-only indexing is a mild pain it works around; do better, like tldraw).
8. **Live run-state overlay on the canvas** (node status, pinned/cached data) as the playback UX.

## 7. The synthesis tension this raises (for the later combination pass)

n8n is **imperative/push** (snapshot → run → done); tldraw is **reactive/pull** (observe the store). Eido's "one graph, three views" must reconcile these. The clean resolution suggested by reading both:

> **The semantic/canvas graph is the reactive source of truth (tldraw-style store). A "playback" takes a snapshot of the relevant subgraph, runs it imperatively (n8n-style engine), and writes results back into the store as new nodes/edges (e.g. an OUTPUT `v3`).** The run is a first-class *record* (for history/timeline), not a mutation of the live graph.

This keeps the canvas reactive and editable while playback runs deterministically — and makes every run part of the "idea evolution timeline." This is a hypothesis to validate in the combination pass, not a decision here.

## 9. Verdict (CTO take)

n8n proves Eido's most novel feature — **executable thought-paths** — is a solved engineering problem with a well-understood shape: a data-driven stack machine over a directed, typed-edge graph, with fan-out/fan-in/loops, item streams, upstream references, retries, and pause/resume. Eido should **borrow these execution semantics wholesale (as patterns, not code)** and spend its own effort on the two things n8n doesn't have: (a) each node's execution being *"compile weighted-graph context → LLM"*, and (b) the live, on-canvas *feel* of watching a thought play back. The big architectural decision n8n surfaces — reactive store vs imperative run — has a clean answer (§7) that preserves the "one graph, three views" thesis: **the graph is reactive; a run is an imperative snapshot whose results flow back as records.**
