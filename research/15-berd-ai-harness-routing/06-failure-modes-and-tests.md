# BERD failure modes and tests

Research lane: provider-routing reliability, installation, process lifecycle, and test evidence.

Repository snapshot: BERD commit [`874e078c931c14386a7d2e16cfe3b32cdbe295e0`](https://github.com/block/berd/tree/874e078c931c14386a7d2e16cfe3b32cdbe295e0), inspected from the local checkout at `research/repos/berd`. The source snapshot is dated 2026-08-21. Official pull requests and commits are linked where they provide design history. This is a source-and-test audit; BERD's complete test suite was not executed.

Evidence key:

- **Strong** — implementation, focused tests, and/or an official PR/commit explain the same failure mode.
- **Medium** — implementation plus focused tests, but no public history item was needed to establish the reason.
- **Inference** — a design implication or risk visible in the implementation, not proof of a production incident.

## Executive verdict

BERD's difficult routing work is not the final `claude` versus `codex` dispatch. It is preserving identity and authority across a changing system boundary:

1. install a native bridge with reproducible provenance and leave a working fallback if the network, registry, or platform changes;
2. launch the right process in the right shell environment and clean up only the process instance actually owned by BERD;
3. keep a session's harness/provider/model tuple coherent while asynchronous loads, picker changes, ACP observations, and reconnects race;
4. do not send a message until the backend session and the provider/model acknowledgement are real;
5. preserve order and ownership when JSON notifications, tool calls, images, and text arrive interleaved; and
6. treat provider discovery as fallible inventory rather than as permission to erase a last-known-good selection.

That is the main lesson for Eido: make the provider adapter a deep reliability boundary. A provider should be more than a command string. It needs installation provenance, environment construction, process identity, session identity, readiness state, stream framing, permissions, and an explicit recovery policy.

## Failure-mode dossier

### 1. Install, stale binaries, registry drift, and retries

The most valuable BERD history is [PR #48](https://github.com/block/berd/pull/48). Its description says startup reconciliation previously installed `@latest` bridges without immutable version or expected integrity, and that pinning only the root package was insufficient because transitive dependency ranges could change. The old post-hoc graph grading was also availability-fragile: re-running `npm install package@version` could resolve a different graph after an upstream publish, leaving a fresh user without a codex bridge. BERD's corrective shape is unusually explicit:

- a checked-in release lock is the npm input, not merely a grader;
- the package and lockfile are staged into a private directory;
- `npm ci` is run without a package spec, with production/optional dependencies and target selectors controlled by BERD;
- the expected root and transitive graph, SRI/integrity data, and physical native executable are verified;
- only then are the shim and state committed;
- failed reconciliation is recorded and retried on a later launch, while the old working bridge remains;
- stale managed Node runtimes are pruned only after the complete reconciliation succeeds.

The tests make the invariants concrete: exact lock pins and integrity, no floating package spec, clearing inherited `npm_config_os`/`cpu`/`libc`, trusted target selectors, missing/extra/mismatched graph entries, missing native executable, failed npm preserving the previous tree/shim/state, and version-specific transaction rollback. This is a better model for Eido than “run npm once during setup.”

The implementation's transaction journal also handles interrupted replacement. It validates journal paths, recovers pending and committed journals, cleans stale temporary stages, rolls every artifact back on a move failure, and leaves evidence if rollback itself fails. That is a non-obvious operational requirement: an install can be interrupted between renaming the bridge tree, shim, and state, so those artifacts need one recoverable commit unit.

### 2. Process cleanup and process identity

BERD's process layer avoids a common harness-wrapper bug: a stale PID can be reused by an unrelated process after the original harness exits. Windows recovery records PID, kernel creation time, and executable path, re-probes all three, and kills only on an exact identity match. If identity is gone, mismatched, or unverifiable, it does not claim ownership. Tests cover identity stability and mismatched creation times. BERD also applies `CREATE_NO_WINDOW` to subprocesses on Windows.

The [official process-recovery commit](https://github.com/block/berd/commit/5dea715f) adds important context: it retains a process handle, uses bounded waits, writes atomic per-process recovery records, and only kills a positive absence/verified child. It explicitly notes that BERD does **not** claim race-free child-tree ownership. That limitation matters to Eido: “kill the process tree” is not a safe abstraction unless the platform gives a verifiable ownership primitive. At minimum, record process identity, executable, launch nonce or handle, and shutdown evidence; make uncertain cleanup visible and retryable.

### 3. Shell PATH and directory environment

Provider CLIs frequently work in a user's terminal but fail when launched by an app because `PATH`, `mise`, `direnv`, Hermit, or a login shell differs. BERD treats this as a provider boundary. `dir_env.rs` runs the user's shell in the requested directory with an interactive login invocation, asks it to emit NUL-delimited environment data, discards shell stdout/stderr so banners cannot corrupt the protocol, and bounds the capture. Results are cached per directory for an hour and concurrent requests share an in-flight capture; failed captures are not cached.

`path_env.rs` then sanitizes and composes PATH, filters unwanted `.hermit` entries unless explicitly preserved, prepends managed tool directories in a deterministic order, falls back to the process PATH if shell capture fails, drops malformed entries instead of producing an empty PATH, and deduplicates entries. These are precisely the “works in my shell” edges an Eido headless invocation will hit. Record the resolved executable and effective environment (redacted) with a run so failures can be diagnosed without asking the user to guess which shell was used.

### 4. Session identity, stale observations, and concurrent target changes

BERD separates three notions that are easy to collapse:

- the **desired** selection from the picker/CLI;
- the **acknowledged** backend target after `set_provider`/`set_model`; and
- an **observed** ACP snapshot returned by session discovery.

`sessionTargetReducer.ts` stores unresolved, settled, transitioning, and failed states. Every transition carries an operation ID and phases. The coordinator is a per-session actor: it coalesces latest-wins work before wiring, owns a dispatch lease while a target mutation is in flight, and refuses stale ACKs, mismatched provider/model snapshots, and external hydration while the lease is held. If backend configuration fails, the previous settled target remains the fallback while the desired target remains visible as failed/unresolved.

The tests cover the races most likely to corrupt Eido's model: stale on-wire operations cannot commit, a wire snapshot arriving before the promise still commits through the coordinator, request IDs/provider IDs/model IDs must all match, external hydration is deferred while a picker owns the session, and a failed target does not erase the previous fallback. Official commits [“Prevent stale ACP snapshot publication”](https://github.com/block/berd/commit/5db65e91) and [“fence stale provider preparation”](https://github.com/block/berd/commit/6891d584) corroborate that these are deliberate fixes, not merely ornamental state types.

For Eido, the practical rule is: a provider/model string in a UI event is not enough to route a prompt. Carry a target generation or request ID from selection through preparation, prompt admission, and persistence. Only the operation that still owns the session may publish the new target.

### 5. Session creation, queued sends, and resume

[PR #61](https://github.com/block/berd/pull/61) documents a production race in the global composer: a background drain saw a draft UUID before backend session creation had promoted it, so the queued message was sent to a nonexistent resource. The fix makes `creationState == null` an attemptability gate; both sender paths reject before the wire, and the queue holds work until the session is promoted. [PR #64](https://github.com/block/berd/pull/64) extends the same admission model so a composer can accept text while preparation runs, but dispatch remains blocked until the session is ready, while failure and read-only paths are retained.

This is especially relevant to a headless CLI where “start a new chat and send the first prompt” is often one command. Eido should make the operation explicit: create/resume session → establish harness/provider/model → receive acknowledged session identity → admit prompt. If creation is pending, queue with a durable ID or return a typed `session_pending` result; never optimistically send by local draft ID.

### 6. JSON streaming, ordering, and backpressure

BERD's `createWebSocketStream` converts a WebSocket into a WHATWG `ReadableStream`. It parses string frames as JSON, ignores malformed JSON, buffers incoming values, wakes pending readers, and closes only after the socket is closed and the buffer drains. Writes wait until the socket opens. This establishes framing and cancellation, but the local adapter has no explicit maximum for its `incoming` array. That is an **inference/risk**, not evidence that BERD has a production memory incident: Eido should decide its own bounded queue/backpressure behavior rather than inherit unbounded buffering by accident. It should also surface malformed frames instead of silently dropping them if those frames could affect a CLI transcript.

The UI stream layer handles the harder ordering problem. It merges contiguous text/thinking updates per session/message/owner and flushes them in one store write per animation frame. Owner tokens prevent an old stream from moving a newer stream's subtitle or active state. The ACP notification handler flushes text before images and tool calls, and late `tool_call_update` events find the exact tool request by `toolCallId`. Tests cover interleaved thinking/text, stale-owner streams, tool calls arriving before first text, tool-result images, and tool request/response/MCP ordering.

For Eido's CLI adapter, model each stream event with `runId`, `sessionId`, `messageId`, `owner/generation`, and `toolCallId` where applicable. Coalesce output for terminal performance, but preserve an append-only event order for recovery and audit. Use a bounded queue with a policy for slow consumers (pause child read, spill to disk, or fail explicitly); do not silently lose events.

### 7. Auth, permissions, and provider boundary

The ACP connection exposes a permission-request handler. If an application handler is registered, it delegates the request; if not, the fallback auto-approves the first option. That fallback may be useful for a tightly controlled internal path, but it is a security-sensitive default for headless Eido and should be treated as a warning, not copied blindly. Eido should require an explicit permission policy (`deny`, `ask`, or a deliberately named non-interactive allow mode), include the requested capability and provider in the audit record, and fail closed when the policy is absent.

BERD's local ACP command also requires a configured Goose WebSocket URL with a non-empty `token` query parameter and validates supported schemes/loopback constraints. Its Goose backend attaches a session credential at the network edge. Separately, [commit `89ee773`](https://github.com/block/berd/commit/89ee77381707f41ecdd080c3c05c4f9f4c1aef18) pins an exact Goose backend commit for a permission fix rather than following `main`. Together these show two useful boundaries: authenticate the local bridge connection explicitly, and pin the backend implementation whose permission behavior the app relies on.

### 8. Provider inventory drift and stranded-provider recovery

[PR #163](https://github.com/block/berd/pull/163) treats an empty discovered model list as potentially non-authoritative. A populated cache is retained, freshness is reset so the next refresh retries, and runtime-managed/configured/provisional inventories are distinguished. The cache uses single-flight refresh and generation fencing so an older result cannot overwrite a newer one. Tests cover stale persisted empties, fresh empty results, configured provisional models, absent cache, and replacement after a later successful refresh.

When a provider is genuinely unavailable, `strandedProviderRecovery.ts` limits automatic recovery to a new session with no backend messages and no local assistant turn. It preserves the failed user text in the new composer, rechecks the current selection immediately before recreation, and does not clobber a newer selection. Eido should copy this conservative boundary: preserve user work, recover only before committed conversation state exists, and make inventory freshness/retry semantics explicit.

## What Eido should copy

1. **Define a provider identity record.** Include `harnessId`, provider ID, concrete model ID, adapter/version, executable path, install provenance, effective working directory/environment fingerprint, auth mode, permission policy, and lifecycle state. A name such as “Claude” is presentation, not routing identity.

2. **Make installation a recoverable transaction.** Stage an exact dependency/artifact manifest, verify the full graph and executable, atomically commit adapter plus metadata, retain the previous working version, and retry failed reconciliation. Prune only after all required providers pass.

3. **Use a per-session actor.** Serialize provider/model preparation, load/resume, and prompt; carry operation ID/generation; accept ACKs only when provider/model/session identity still matches; fence external hydration with a lease.

4. **Gate prompt admission.** Require a real backend session ID and acknowledged provider+model. If creation is pending, queue durably or return a typed pending result. If a mutation times out, invalidate/reconnect before the next remote mutation.

5. **Make the stream adapter explicit.** Parse framed JSON, report malformed frames, bound the queue, preserve event order, support cancellation, coalesce terminal output without dropping the append-only event log, and associate tool updates by exact ID.

6. **Model inventory truth states.** Distinguish authoritative, provisional, stale, and retryable-empty results. Preserve last-known-good models and selection through transient discovery failure.

7. **Make safety policy explicit.** Require authenticated local bridge edges, process identity checks, and a permission policy. Eido should not inherit BERD's auto-approve fallback as a silent default for headless runs.

## Limits and interpretation

- Findings about code behavior are from the pinned source snapshot. PR descriptions are historical evidence of why particular safeguards were added, not a claim that every earlier defect remains in the pinned tree.
- This lane inspected focused tests and source; it did not execute BERD's full Rust/TypeScript test suite.
- The WebSocket adapter's unbounded `incoming` array is an implementation observation and design caution, not a reported BERD incident.
- BERD's Windows recovery deliberately does not claim race-free child-tree ownership; Eido should preserve that humility rather than overstate “process tree cleanup.”
- The ACP permission fallback auto-approves the first option when no handler is provided. The code establishes the fallback; it does not by itself establish how often production runs without a handler. Treat the behavior as a security-review item.
